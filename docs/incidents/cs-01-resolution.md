# CS-01: 가격 정렬 후 페이지 분할

관련 이슈: [#9](https://github.com/dongho-dev/fault-commerce-lab/issues/9)

## 재현과 원인

`incident/cs-01`의 `6f037c6`에서 낮은가격순 요청은 DB에 상품 ID순 조회를 보내고,
`LIMIT`과 `OFFSET`으로 가져온 한 페이지의 상품만 Python에서 가격순으로 정렬했다.
페이지 안의 가격은 오름차순이어도 다음 페이지에서 더 싼 상품이 나올 수 있었다.

가격이 3,000 / 1,000 / 2,000 / 1,000 / 3,000 / 2,000원인 상품을 순서대로 등록하고
2개씩 조회하면, 수정 전에는 전체 가격 순서가
1,000 → 3,000 → 1,000 → 2,000 → 2,000 → 3,000원이 되어 회귀 테스트가 실패했다.

## 수정과 정렬 규칙

한 페이지만 정렬하던 낮은가격순 전용 분기를 제거하고 기존 공통 DB 조회를 사용한다.
검색·카테고리 조건에 맞는 결과에 정렬 기준을 적용한 뒤 요청한 페이지 범위를 가져온다.

| 선택 | 우선 기준 | 가격이 같을 때 |
| --- | --- | --- |
| 낮은가격순 | `unit_price ASC` | `id ASC` |
| 높은가격순 | `unit_price DESC` | `id ASC` |

기존 API의 `limit`·`offset`, 페이지 번호 UI, Oracle, API 계약, DB 불변조건은 유지한다.

## 검증 결과

2026-10-06, 격리된 PostgreSQL 16 환경에서 확인했다.

- 수정 전: 추가한 페이지 경계 회귀 테스트가 실제 순서 오류로 실패했다.
- 수정 후: 기존 카탈로그 9개와 새 회귀 사례 24개, 총 33개 테스트가 통과했다.
  낮은가격순·높은가격순, 동가 ID 오름차순, 페이지 크기 2·3·20,
  전체·검색·카테고리·검색과 카테고리 조합, 품절 상품, 마지막 빈 페이지를 확인했다.
- 현재 수정 코드를 대상으로 `python -m lab_suite.operator check --expect healthy --fresh`가 통과했다.
  41개 상품을 20·20·1개로 보여주는 Linux Chromium 화면과 API 순서가 일치했다.
  1페이지는 1,000~20,000원, 2페이지는 21,000~40,000원, 3페이지는 41,000원이었다.
  페이지 크기 7·13·41, 같은 가격의 반복 조회, 다른 정렬·필터 대조군까지
  실습 판정 9개와 Oracle이 통과했다.
- 변경한 Python 파일의 Ruff 린트·형식 검사가 통과했다.
- 검증 환경은 종료했다. 실습 결과는 새 임시 DB에서 수행한 코드 검증이다.

로컬 실습 증거는 `artifacts/cs-labs/learner-01/20261006T112112.593481Z-check/`에 남긴다.
저장소 전체 테스트나 부하·지연 측정은 이번 검증에 포함하지 않았다.

## 고려한 UX와 작업 범위

가격을 비교하는 고객에게는 초반 몇 페이지를 빠르게 제공하는 것이 중요하고,
50페이지나 마지막 페이지로 바로 이동하는 동작은 상대적으로 후순위라는 의견을 기록했다.
커서 방식, 인덱스 튜닝, 응답 속도 최적화는 이번 정렬 오류 수정 범위에 포함하지 않았다.

고객 안내: 같은 검색어와 카테고리에서 낮은가격순을 선택하면 전체 결과의 낮은 가격부터,
높은가격순을 선택하면 높은 가격부터 페이지에 표시된다. 같은 가격은 상품 ID 오름차순이다.
검증은 조회 사이에 상품·가격이 바뀌지 않는 조건이며, 여러 요청에 걸친 시점 고정 기능은 제공하지 않는다.
