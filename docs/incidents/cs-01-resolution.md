# CS-01 해결 과정: 낮은가격순의 페이지 순서 복구

낮은가격순에서 다음 페이지에 더 싼 상품이 나타나는 이유를 DB 반환값부터 확인했다.
DB 조회가 상품 ID순으로 페이지를 먼저 나누고, 서버가 그 페이지 안에서만 가격순으로
정렬하는 것이 원인이었다. DB에서 가격과 ID로 정렬한 결과에 페이지 범위를 적용하도록 수정했다.

- 문제: [이슈 #9](https://github.com/dongho-dev/fault-commerce-lab/issues/9)
- 수정 제안: [PR #19](https://github.com/dongho-dev/fault-commerce-lab/pull/19)
- 조사 대상: `incident/cs-01`, 커밋 `6f037c6`
- 구현 커밋: [029a1de](https://github.com/dongho-dev/fault-commerce-lab/commit/029a1de2ad3e9985d835c2e0b56c95a000c802f6)
- 확인 날짜: 2026-10-06

이 문서는 합성 상품을 사용하는 학습용 실습의 해결 기록이다. 실제 고객 트래픽이나 운영 장애 통계는 아니다.

## 1. 어떤 문제부터 확인했나

이슈의 증상은 “한 페이지 안에서는 낮은가격순처럼 보이지만, 다음 페이지에서 더 싼 상품이 나온다”였다.
이 설명만으로는 DB 조회, 서버의 응답 가공, 화면 표시 중 어느 단계가 원인인지 알 수 없었다.
따라서 **낮은가격순 요청을 받았을 때 DB가 실제로 어떤 순서로 반환하는지**부터 확인했다.

초기 가설은 가격 정렬보다 페이지 분할이 먼저 적용된다는 것이었다.
아래의 DB 조회문과 반환 순서, API 응답 비교로 이 가설을 확인했다.

## 2. DB 반환값과 API 응답을 비교했다

수정 전 코드를 격리된 PostgreSQL 16에 연결했다. 상품 생성 API로 다음 상품을 순서대로 등록했다.
DB 데이터를 직접 바꾸거나 API 응답을 모킹하지 않았다.

| 상품 ID | 1 | 2 | 3 | 4 | 5 | 6 |
| --- | --- | --- | --- | --- | --- | --- |
| 가격 | 6,000원 | 1,000원 | 4,000원 | 5,000원 | 2,000원 | 3,000원 |

검색어 `CS01-DB-ORDER`, 카테고리 `digital`, 정렬 `price_asc`를 유지하고,
`limit=3`에 `offset=0`, `offset=3`을 각각 적용했다.
FastAPI TestClient로 API 경로를 실행하면서 실제 SQL과 서버가 재정렬하기 전의 DB 행 순서를 수집했다.
관측용 처리를 제거하고 다시 요청했을 때도 API 결과가 같았다.

| 관측 단계 | 1페이지 | 2페이지 |
| --- | --- | --- |
| DB가 반환한 가격 순서 | 6,000 → 1,000 → 4,000원 | 5,000 → 2,000 → 3,000원 |
| API가 반환한 가격 순서 | 1,000 → 4,000 → 6,000원 | 2,000 → 3,000 → 5,000원 |

실제로 실행된 SQL의 정렬 기준은 `ORDER BY products.id`였다.
1페이지에는 `LIMIT 3 OFFSET 0`, 2페이지에는 `LIMIT 3 OFFSET 3`이 적용됐다.
DB에는 가격순으로 반환하라는 조건이 전달되지 않았다.

서버는 이 결과에 `sorted(rows, key=lambda row: (row[0].unit_price, row[0].id))`를 적용했다.
이미 가져온 세 상품만 정렬하므로, 2페이지의 2,000원·3,000원 상품을 1페이지로 옮길 수 없었다.
API 응답 자체에서 순서가 깨져 있어 화면에 도착하기 전에 문제가 발생한다는 것도 확인했다.

## 3. 정렬 규칙과 이번 수정 범위를 정했다

검색 조건에 맞는 **전체 결과의 순서를 먼저 정하고, 그 순서에서 요청한 페이지의 상품만 가져온다.**
같은 가격일 때는 ID 오름차순으로 순서를 고정한다.

| 사용자가 선택한 정렬 | 우선 기준 | 가격이 같을 때만 |
| --- | --- | --- |
| 낮은가격순 | 가격 오름차순 | ID 오름차순 |
| 높은가격순 | 가격 내림차순 | ID 오름차순 |

예를 들어 높은가격순에서는 `10,000원(ID 3) → 10,000원(ID 8) → 5,000원(ID 2)`가 된다.
높은가격순의 기존 동작도 이 규칙을 따르고 있어, 수정과 함께 회귀 테스트로 확인했다.

가격을 비교하는 고객에게는 초반 몇 페이지를 빠르게 제공하는 것이 중요하고,
50페이지나 마지막 페이지로 바로 이동하는 동작은 상대적으로 후순위라는 UX 의견을 기록했다.
다만 이번 이슈는 정렬 정확성에 한정했다. 기존 `limit`·`offset`과 페이지 번호 UI를 유지하고,
커서 방식·인덱스 튜닝·응답 속도 최적화는 후속 고려 사항으로 남겼다.

## 4. 한 페이지 안에서만 정렬하던 분기를 제거했다

[상품 조회 코드](../../app/repositories/product.py#L63)에서 낮은가격순 전용 분기를 제거했다.
기존 공통 조회의 다음 순서를 사용한다.

```python
.where(*conditions)
.order_by(*order_clauses(sort), Product.id)
.limit(limit)
.offset(offset)
```

낮은가격순의 정렬 기준은 `ORDER BY unit_price ASC, id ASC`,
높은가격순은 `ORDER BY unit_price DESC, id ASC`다.
서버가 전체 상품을 내려받아 페이지별로 나누는 방식으로 변경하지 않았다.
DB가 정렬 기준에 맞춰 해당 페이지의 상품만 반환한다.

Oracle, API 계약, DB 불변조건, 기존 테스트의 기대값은 수정하지 않았다.

## 5. 새 테스트가 수정 전 오류를 잡는지 확인했다

기존 카탈로그 테스트는 낮은가격순을 한 페이지 안에서 확인했다.
낮은가격순의 페이지 경계 오류를 잡을 검사가 필요해
[회귀 테스트](../../tests/integration/test_price_pagination.py)를 추가했다.

동가 상품도 포함하도록 별도의 상품 6개를
`3,000 / 1,000 / 2,000 / 1,000 / 3,000 / 2,000원` 순서로 생성했다.
첫 DB 조사에 사용한 상품 6개와는 다른 테스트 데이터다.

| 두 개씩 조회한 전체 결과 | 상품 ID 순서 | 가격 순서 |
| --- | --- | --- |
| 수정 전 관측값 | 2 → 1 → 4 → 3 → 6 → 5 | 1,000 → 3,000 → 1,000 → 2,000 → 2,000 → 3,000원 |
| 기대값·수정 후 결과 | 2 → 4 → 3 → 6 → 1 → 5 | 1,000 → 1,000 → 2,000 → 2,000 → 3,000 → 3,000원 |

수정 전 코드에서 해당 회귀 테스트가 순서 불일치로 실패하는 것을 먼저 확인했다.
그 뒤 구현을 수정했고, 기존 카탈로그 테스트 9개와 새 회귀 사례 24개가 모두 통과했다.

새 사례 24개는 가격 정렬 2종 × 페이지 크기 3종(2·3·20) × 검색 조건 4종의 조합이다.
검색 조건은 전체, 검색어, 카테고리, 검색어와 카테고리 조합이다.
각 조합에서 가격·동가 ID 순서, 품절 상품의 위치, 결과 개수와 페이지 정보,
전체 상품의 누락·중복 여부, 마지막 빈 페이지까지 확인했다.

## 6. 실제 브라우저와 Oracle로 확인했다

수정한 현재 체크아웃을 대상으로 다음 실습 검증을 실행했다.

```powershell
python -m lab_suite.operator check --expect healthy --fresh
python -m lab_suite.operator down
```

새 임시 DB의 41개 상품을 Linux 컨테이너 안의 Chromium에서 20개씩 조회했다.

| 화면 | 표시 개수 | 가격 범위 |
| --- | --- | --- |
| 1페이지 | 20개 | 1,000~20,000원 |
| 2페이지 | 20개 | 21,000~40,000원 |
| 3페이지 | 1개 | 41,000원 |

브라우저의 상품 순서가 API 응답과 일치했고 페이지 경계에서도 가격순이 이어졌다.
페이지 크기 7·13·41, 동가 상품의 반복 조회, 다른 정렬·필터 대조군을 포함한

실행 로그와 화면 캡처는 로컬의

검증 후 실습 컨테이너와 네트워크는 종료·제거했다.

## 7. 고객 안내와 검증 범위

같은 검색어와 카테고리에서 낮은가격순을 선택하면 전체 결과의 낮은 가격부터,
높은가격순을 선택하면 높은 가격부터 페이지에 표시된다.
같은 가격은 상품 ID 오름차순으로 표시하므로 순서가 명확하게 정해진다.

이 기록은 새 임시 DB에서 확인한 코드 수정 결과다. 기존 운영 데이터의 복구 검증은 수행하지 않았다.
검증 중에는 조회 사이에 상품·가격을 변경하지 않았고, 여러 요청에 걸친 시점 고정 기능은 제공하지 않는다.
저장소 전체 테스트와 부하·지연 측정은 이번 검증 범위에 포함하지 않았다.
