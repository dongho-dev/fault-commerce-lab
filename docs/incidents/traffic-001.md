# TRAFFIC-001 해결 기록: 몰리는 시간대에 목록·검색이 느려짐

고객 문의(VOC)에서 시작해 목표를 정하고, 측정으로 원인을 좁히고, 고친 뒤 다시 측정해 판정하기까지의
과정을 순서대로 기록합니다. 모든 수치는 2026-10-06, `docs/capacity-baseline.md`와 같은 서버 크기
(앱 CPU 1개, 메모리 512MB, 워커 1개)에서 측정했습니다.

## 1. 증상: 고객 문의 (GitHub 이슈 #1)

| # | 고객 문의 요지 |
| --- | --- |
| 1 | 생활용품 카테고리를 누르면 목록이 한참 뒤에 한꺼번에 뜬다 |
| 2 | '커피' 검색 결과가 바로 안 나와 여러 번 눌렀다 |
| 3 | 카테고리를 넘길 때마다 기다려야 하고, 저녁 시간에 특히 심하다 |
| 4 | 상품 상세·주문도 가끔 버벅이지만 주문은 정상 처리됐다 |
| 5 | 오류는 없는데 전체적으로 굼뜨고, 한가할 때는 괜찮다 |

공통점은 **에러 없이 느림**, **사람이 몰릴 때 심함**, **목록·검색이 가장 심함**입니다.

## 2. 문의를 화면 단위로 재현해 측정

고객은 API가 아니라 화면을 봅니다. 그래서 프론트가 화면 하나를 열 때 보내는 요청 묶음을 그대로
재현하고, 화면이 완성될 때까지 걸린 시간을 쟀습니다(`scripts/voc_probe.py`).

- 목록·검색 화면은 요청 9개를 병렬로 보냅니다: 본 목록 1개 + 개수 조회(`limit=1`) 8개.
- 상세 화면은 상세 API → 관련 상품 목록, 주문은 재고 확인 → 주문을 차례로 보냅니다.
- 다른 사용자 0명·10명·20명을 배경 부하로 걸고, 조건마다 12회 측정했습니다.

| 문의 | 0명 | 10명 | 20명 |
| --- | --- | --- | --- |
| 1. 카테고리 목록 | 569 / 839 | 1,090 / 1,506 | 1,700 / 2,036 |
| 2. 검색 | 538 / 908 | 946 / 1,378 | 1,443 / 1,977 |
| 3. 카테고리 3개 넘기기 | 1,805 / 2,089 | 3,111 / 3,404 | 4,984 / 5,511 |

### 공통된 것과 독립된 것

- **공통**: 사람이 몰리면 모든 화면이 느려지고, 앱 CPU가 1개에 붙어 있으며 DB는 거의 놀고 있다.
  병목은 앱이다.
- **독립**: 목록·검색 화면은 **혼자 써도** 0.55초가 걸린다. 상세·주문은 혼자 쓰면 정상(9~17ms)이고
  몰릴 때만 느리다. 즉 목록·검색이 원인 후보이고, 상세·주문은 같이 느려지는 쪽으로 보인다.

## 3. 목표 설정 (1차)

고객 체감 기준(0.1초 즉시, 0.5초 이하 답답하지 않음, 1초 이상이면 멈췄다고 느끼고 다시 누름)으로
동시 사용자 20명 기준 화면 p95 목표를 정했습니다.

| 문의 | 1차 목표 |
| --- | --- |
| 1·2. 목록·검색 | 500ms 이하 |
| 3. 카테고리 3개 넘기기 | 넘길 때마다 500ms, 합계 1,500ms 이하 |
| 4a. 상품 상세 | 300ms 이하 |
| 4b. 주문 | 500ms 이하 |
| 혼자 쓸 때 목록·검색 | 200ms 이하 |
| 부하 테스트 | 20명에서 SLO PASS (p95 ≤ 300ms, p99 ≤ 1s), 용량 20명 이상 |

> 이 목표는 정상 시스템의 화면 수치를 재지 않고 정했습니다. 7장에서 이 점을 바로잡습니다.

## 4. 요청 내부를 단계별로 분해

앱 컨테이너 안에서 라우트 함수를 실제 세션으로 호출하면서, 저장소·서비스 메서드와 SQL 실행에
타이머를 걸었습니다(`scripts/stage_profile.py`). 같은 요청을 HTTP로도 보내 앱 밖에서 기다린 시간을
구했습니다.

### 한가할 때 (중앙값, ms)

| 단계 | 목록 | 개수 조회 (`limit=1`) | 검색 | 상세 | 주문 |
| --- | --- | --- | --- | --- | --- |
| `units_sold_by_product` (추천순용 판매량) | **58.7** | **39.5** | **36.7** | 없음 | 없음 |
| └ 그중 SQL 실행 | 4.3 | 4.2 | 4.3 | | |
| └ 읽은 행 | 4,526 | 4,526 | 4,526 | | |
| 목록·개수 SQL | 2.6 | 2.3 | 3.3 | | |
| 상품·재고 조회, 재고 차감, 주문 저장 | | | | 1.8 | 3.6 |
| 변환·직렬화 | 0.1 미만 | 0.1 미만 | 0.1 미만 | 0.1 미만 | 0.1 미만 |
| 앱 내부 합계 | 61.7 | 43.3 | 41.3 | 2.2 | 5.2 |

### 동시 사용자 20명 (중앙값, ms)

| | 목록 | 개수 조회 | 검색 | 상세 | 주문 |
| --- | --- | --- | --- | --- | --- |
| 앱 내부 합계 | 141.8 | 137.0 | 95.8 | 3.3 | 15.9 |
| HTTP 전체 | 855.0 | 816.5 | 811.7 | 538.3 | 529.2 |
| 대기 시간 (HTTP − 앱 내부) | 713 | 680 | 716 | 535 | 513 |

### 해석

- **독립 문제 A**: 목록·검색 요청은 추천순 정렬을 위해 매번 **주문 테이블 전체**를 `Order` 객체로
  읽어 파이썬 반복문으로 상품별 판매량을 합산한다. 요청 시간의 90~95%가 여기서 나온다.
  상품 1개만 받는 개수 조회도 똑같이 전체를 읽는다. 읽는 행 수는 주문 수와 같아서 주문이 쌓일수록
  느려진다.
- 화면 하나는 요청 9개이므로 약 9 × 50ms ≈ 0.45초 동안 CPU 1개를 혼자 쓴다. 혼자 써도 0.55초,
  앱 CPU 77%라는 화면 측정과 맞는다.
- 실제로 쓰이는 결과는 화면의 상품 20개 판매량뿐이다. 홈·리빙 카테고리는 주문이 0건이라
  5,105행을 합산한 결과가 전부 0이다.
- **공통 문제 B**: 부하가 걸리면 모든 요청에 500~700ms의 대기 시간이 붙는다. 상세는 앱 안에서
  3ms면 끝나지만 CPU 1개 앞에서 줄을 선다. 줄을 만드는 주범은 A로 추정한다.

### 같은 O(N)인데 왜 느린가

SQL 실행은 4.3ms뿐이고, 나머지 약 47ms는 앱이 받은 행을 파이썬 값으로 변환하고, ORM 객체로
만들고(9칸, 변경 추적, identity map 등록), 반복문으로 더하는 데 쓰였다. 한 줄당 약 10µs이다.
DB 안에서 같은 행을 훑어 합산하면 한 줄당 약 0.17µs이다. 차이는 줄 수가 아니라 **한 줄당 비용**과
**그 일을 CPU가 가장 부족한 앱에서 한다는 점**이다.

## 5. 선택지 비교

| 선택지 | 속도 | 정확성 | 수정 범위 | 위험 |
| --- | --- | --- | --- | --- |
| **A. DB에서 화면 상품만 합산** (`GROUP BY` + `IN`) | 빠름 | 항상 최신 | 함수 1개 | 아주 큰 규모에서 다시 느려질 수 있음 |
| B. 판매량 = 초기 재고 − 현재 재고 | 가장 빠름 | 지금은 일치 | 함수 1개 | 반품·재입고가 생기면 틀어짐 |
| C. 판매량 요약 테이블 | 가장 빠름 | 최신 | 스키마 + 주문 로직 | 인기 상품 행 잠금 경합 |
| D. 판매량 캐시 (TTL) | 대체로 빠름 | 지연 반영 | 작음 | 원인은 그대로, 갱신 시 스탬피드 |
| E. 스케일 업·아웃 | 조금 나아짐 | 그대로 | 설정 | 주문이 늘면 비용도 계속 늘어남, DB 커넥션 한도 |
| F. 상품 1개 이하면 정렬 생략 | 화면 비용 1/9 | 그대로 | 아주 작음 | 단독으로는 부족 |

**결정: A.** 원인(필요 없는 전체 읽기)을 직접 없애고, 판매량의 의미·API 계약·DB 불변조건을 바꾸지
않습니다. 재사용 캐시(D)는 A로 계산이 1~2ms가 된 뒤에는 아낄 몫이 작아서 보류했습니다. 스케일
업·아웃(E)은 급할 때 시간을 버는 임시 조치로만 봅니다.

수정 전에 두 쿼리를 그대로 실행해 효과를 미리 확인했습니다(주문 5,105건, 30회 중앙값).

| 방식 | p50 | p95 |
| --- | --- | --- |
| 기존: 전체 주문을 객체로 읽어 합산 | 51.6ms | 63.0ms |
| A: 홈·리빙 페이지 상품 (주문 0건) | 0.9ms | 1.3ms |
| A: 가장 많이 팔린 상품 20개 (가장 나쁜 경우, 주문 2,772건 합산) | 1.8ms | 2.2ms |

## 6. 수정

`app/repositories/order.py`의 `units_sold_by_product`가 화면에 나올 상품 ID만 받아 DB에서 합산하도록
바꾸고, `app/services/product.py`에서 페이지 상품 ID를 넘깁니다.

```python
select(Order.product_id, func.sum(Order.quantity))
    .where(Order.product_id.in_(product_ids))
    .group_by(Order.product_id)
```

- 상품 131개 전부에서 기존 방식과 판매량이 같음을 확인했습니다.
- ruff, mypy, pytest 52개 통과. API 계약·DB 스키마·Oracle은 바꾸지 않았습니다.

### 화면 측정과 1차 목표의 충돌

12회 측정에서는 상세 하나만 목표를 넘었지만, 40회로 늘리자 검색(531ms)과 상세(528ms)가 넘었습니다.
12회에서는 p95가 사실상 최댓값이라 흔들림이 큽니다.

"고친 게 덜 된 것인가, 목표가 잘못된 것인가"를 가르려면 정상 시스템과 비교해야 합니다. 처음에는 정상
기준을 새 스택으로 띄워 비교했지만, 두 스택의 데이터 규모가 달랐습니다(정상 기준 주문 1,937건,
수정 후 5천여 건). 측정할 때마다 주문이 쌓이므로 데이터가 다르면 비교가 성립하지 않습니다.

### 같은 데이터로 세 버전 비교

문제가 보고된 시점의 데이터를 기준 데이터로 정했습니다. 이슈가 등록된 시각(2026-10-06 03:50:50Z)까지
만들어진 상품 68개와 주문 3,419건만 떠내고, 재고는 그 시점까지의 주문으로 다시 계산했습니다(재고
불변조건 위반 0건). 정상 기준(`l1-baseline-v2`), 장애 상태(`b2d3603`), 수정 후를 각각 띄우고,
**측정할 때마다 이 데이터로 되돌린 뒤** 화면 측정(40회, 정상 기준 4번, 나머지 2번)과 부하 테스트를

### 해석

- **장애는 같은 데이터에서도 재현된다.** 정상 기준보다 화면이 4~6배 느리고, 용량이 20명에서 5명으로
  떨어진다. 혼자 쓸 때도 목록이 4.5배 느리다.
- **수정 후는 정상 기준 수준으로 돌아왔다.** 용량 20명, SLO PASS이고 화면들도 정상 기준 범위 안이거나
  근처다.
- **화면 p95는 같은 코드에서도 크게 흔들린다.** 정상 기준의 상세 화면이 네 번 측정에서 164~470ms였다.
  20명은 이 서버의 용량 한계(앱 CPU 평균 91%)라 꼬리 지연이 튄다. 버전 간 판정은 요청 수천 건을 합친
  부하 테스트를 주 근거로 삼는다.
- **수정 후는 정상 기준보다 약간 무겁다.** 처리량 −7%, 부하 p95 +17%, 혼자 쓸 때 목록 +10~13%이다.
  데이터를 맞춰도 남았으므로 코드 차이다. 정상 기준에는 "많이 팔린 순" 정렬 기능이 아예 없었고,
  수정 후는 이 기능을 유지하면서 목록 요청마다 판매량 쿼리 하나(약 1~2ms)를 더 쓴다. 장애의 원인은
  이 기능의 비효율적인 구현이었고, 남은 차이는 기능 자체의 비용이다.

근거로 최종 목표를 다시 정했습니다.

| 정상 기준 대비 | 처리량 −10% 이내 | −7% | 달성 |
| 체감: 화면이 멈춘 것처럼 보이지 않음 | 20명에서 모든 화면 p95 1초 미만 (3개 넘기기는 한 번에 1초 미만) | 최대 566ms, 넘기기 한 번 약 320ms | 달성 |
| 체감: 한가할 때 즉시 | 목록·검색 p95 200ms 이하 | 151 / 143ms | 달성 |
| 기능 | 테스트 52개, Oracle 통과, API 계약 불변 | 통과 | 달성 |

**판정: 해결.** 고객이 문의한 1.4~6초 지연이 문의가 없던 정상 시절 수준(0.4~1초 미만)으로 돌아왔고,
주문이 쌓일수록 느려지던 구조도 사라졌습니다.

## 8. 후속 과제 (별도 이슈)

- 추천순 판매량 재사용: 판매량을 미리 계산해 두면(요약 테이블이나 짧은 TTL 캐시) 남은 7%를 없앨 수
  있다. 순위 반영 지연, 갱신 시 스탬피드, 인기 상품 행 잠금 경합을 함께 검토한다.
- 용량 여유분: 정상 시스템이 평상시 트래픽(10~20명)에서 이미 CPU 90% 이상을 쓴다. 평상시 사용률
  50~70%를 목표로 최적화나 스케일 업을 검토한다. 워커·인스턴스를 늘릴 때는 DB 커넥션 한도(100)를
  함께 조정한다.

## 9. 배운 점

- 목표는 **고객 체감**과 **정상 기준선**을 함께 근거로 세운다. 기준선을 재지 않은 목표는 정상
  시스템도 못 지킬 수 있다.
- p95는 표본이 적으면 최댓값과 같아진다. 판정용 측정은 40회 이상, 가능하면 두 번 이상 잰다.
- 버전을 비교할 때는 데이터를 같은 상태로 맞춘다. 측정 자체가 주문을 쌓기 때문에, 측정할 때마다
  같은 스냅숏으로 되돌린 뒤 시작한다. 기준 데이터는 문제가 보고된 시점의 상태로 정한다.
- 같은 O(N)이라도 한 줄당 비용과 그 일을 어디서 하는지(병목 자원인지)에 따라 수십 배 차이 난다.
- 급할 때는 자원을 늘려 시간을 벌 수 있지만, 데이터가 늘수록 비용이 커지는 낭비는 코드로 고친다.

## 재현 방법

```bash
# 화면 단위 측정 (배경 부하 0·10·20명, 조건마다 ROUNDS회)
docker compose --profile tools run --rm -T --build -e ROUNDS=40 -e CONDITIONS=0,20 \
  --entrypoint python loadgen -m scripts.voc_probe

# 요청 내부 단계 분해 (앱 컨테이너 안에서 실행)
docker compose exec -T app python -m scripts.stage_profile

# 부하 테스트
docker compose --profile tools run --rm --build loadgen --stages 5,10,20,40 --stage-seconds 30 --label after-fix
```

정상 기준을 같은 조건으로 재려면 `git worktree add --detach <경로> l1-baseline-v2`로 작업 폴더를 만들고,
`compose.override.yaml`로 앱의 호스트 포트 매핑을 지운 뒤(`ports: !reset []`) `docker compose -p shop1-base`로
띄워 같은 명령을 실행합니다. 측정 스크립트는 기준 태그에 없으므로 표준 입력으로 넘깁니다
(`--entrypoint python loadgen - < scripts/voc_probe.py`).

같은 데이터로 비교할 때는 기준 시각까지의 `products`·`orders`를 `\copy (SELECT ... WHERE created_at <= ...)`로
떠내고, `inventories.current_stock`은 그 시각까지의 주문 수량으로 다시 계산해 떠냅니다. 측정할 때마다 각
스택의 DB에서 `TRUNCATE orders, inventories, products RESTART IDENTITY CASCADE` 후 세 파일을 `\copy`로
넣고 두 시퀀스를 `setval`로 맞춘 다음, 재고식 위반이 0건인지 확인하고 시작합니다.
