# CS-13: 앱 주소 교체 후 상품 응답 복구

- 문제: [이슈 #26](https://github.com/dongho-dev/fault-commerce-lab/issues/26)
- 수정 기준: `incident/cs-13`의 `843450dcc8212a21c8a91c17c8c239b058e5c5f9`
- 검증일: 2026-10-07, 격리된 Linux 컨테이너와 임시 PostgreSQL

## 문제와 확인한 사실

처음에는 상품 목록과 상세가 보이지만 앱 서버가 교체된 뒤에는 새로 방문하거나 새로고침해도 상품 정보를 받지 못했다.

수정 전 실제 HTTP·브라우저 재현에서는 최초 상품 조회 20건이 모두 정상이었고, 준비된 대체 서버로 두 차례 전환한 뒤 고객 경로의 상품 조회 40건은 모두 `502`였다. 이 40건은 동시 사용자 수가 아니라 순차 요청 20건씩 두 묶음이다. 각 묶음은 목록 10건과 상세 10건이다. 실행 중인 앱에 직접 요청하면 정상 JSON이 나왔다.

추가 관측에서는 원본 프록시 함수를 바꾸지 않고 Python 실행 추적과 해당 Linux 컨테이너의 TCP 패킷을 기록했다. 고객 경로의 요청 6건 모두 TCP 연결, 요청 데이터 ACK, HTTP 핸들러 진입, 응답 데이터 ACK를 확인했다. 정상 응답은 프록시가 읽은 본문과 클라이언트가 받은 본문의 SHA-256이 같았다. 장애 응답은 앱에 연결하는 단계에서 약 1.01초 뒤 실패했다. 상품 JSON을 읽은 뒤 반환하다 손상된 경우가 아니었다.

원인은 `resolve_host()`의 `lru_cache`였다. 서비스 이름을 처음 조회한 IP가 만료 없이 남아 있었다. 관측 당시 실행 중인 앱 주소가 `172.20.0.3`에서 `.6`, `.7`로 바뀌고 최종적으로 `.7`만 남았는데도 프록시는 `.3`을 사용했다. 캐시 조회는 계속 적중하고 실제 이름 조회는 한 번뿐이었다. 이전 앱으로의 연결이 실패하면 프록시는 `502`와 20바이트의 `upstream unavailable`을 반환했다.

최초 재현 커밋은 `1776a047a77659298d11d8a5a9895eb8870b42c1`이다. 이후 수정 기준까지 추가된 두 커밋은 실습 종료 도구 변경이며 프록시 코드는 동일했다.

## 선택한 수정과 주소 갱신 방식

[프록시](../../lab_suite/advanced_proxy.py)에서 별도의 IP 캐시와 단일 IP 해석 함수를 제거하고, `HTTPConnection`에 `catalog-service`라는 호스트 이름을 넘긴다. 원래부터 요청마다 새 연결을 만들고 종료하므로 연결할 때마다 Python의 `socket.create_connection()`이 시스템 이름 해석기인 `getaddrinfo()`를 호출한다.

```text
새 요청 → 서비스 이름 조회 → 반환된 주소에 연결 → 앱 응답을 그대로 고객에게 전달
다음 요청 → 서비스 이름을 다시 조회 → 갱신된 주소에 연결
```

별도의 주기적 갱신 작업이나 애플리케이션 DNS 캐시를 추가하지 않았다. 따라서 이 프록시의 자체 캐시 만료를 기다릴 필요가 없다. 주소의 최신성은 시스템 이름 해석기가 반환하는 결과를 따른다.

이름 조회 결과에 여러 주소가 있으면 표준 라이브러리가 연결에 실패한 주소 다음의 주소를 시도한다. 이는 HTTP 요청을 보내기 전의 연결 선택이다. 이미 보낸 요청을 다시 실행하는 재시도는 추가하지 않았다. 앱이 POST를 받은 뒤 응답 연결을 끊은 경우에도 다른 앱으로 같은 POST를 재전송하지 않는 테스트를 포함했다.

기존 소켓 타임아웃 1초는 유지했다. 타임아웃을 늘리면 오래된 주소를 더 오래 기다릴 뿐 주소 갱신 문제가 해결되지 않는다. 이 1초는 소켓 동작의 제한이며 전체 HTTP 요청이나 이름 조회를 포함한 총 시간 보장은 아니다.

## 검증

[새 회귀 테스트](../../lab_suite/tests/test_advanced_proxy.py)는 실제 루프백 HTTP 서버와 제어 가능한 이름 조회 결과를 사용한다. 실제 Docker 이름 조회와 서버 교체는 기존 실습 판정으로 별도 검증했다.

| 검사 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 새 프록시 회귀 테스트 7개 | 3개 실패, 4개 통과 | 7개 통과 |
| 기존 실습 제어 테스트 6개 | 변경 없음 | 6개 통과 |
| 서버 교체 후 목록·상세 HTTP 조회 40건 | 40건 모두 502 | 40건 모두 200, 전체 상품 내용 일치 |
| 두 차례 교체 후 새 Linux 브라우저의 상품 상세 | 두 번 모두 표시 실패 | 두 번 모두 표시 성공 |
| Oracle | 통과 | 통과 |

회귀 테스트 범위는 두 차례 주소 변경, 첫 주소 연결 실패 시 다음 주소 사용, 일시적인 이름 조회 실패 후 다음 요청 복구, GET·POST 본문 보존, POST 응답 유실 시 요청 재전송 방지다. 수정 후 표적 테스트 합계는 **13개 통과**다. 변경한 Python 파일의 Ruff 검사·포맷 검사와 `git diff --check`도 통과했다.

현재 수정 소스로 `python -m lab_suite.operator check --expect healthy --fresh`를 실행했다. 최초 20건과 교체 후 40건이 모두 유효했고, 교체 제어 절차·브라우저·Oracle을 포함한 정상 판정이 통과했다. 기록은 `artifacts/cs-labs/learner-13/20261007T024046.208889Z-check/`에 남겼다. 사용한 앱 이미지 ID는 `sha256:d44a660b748613c416a0044acc150f32f72505622da3edc54f631975dc454ff5`다.

검증 후 `python -m lab_suite.operator down`으로 이번 실습 컨테이너와 네트워크를 종료했다. 준비된 대체 서버가 정상이고 서비스 이름이 갱신된 조건에서 확인한 결과다. 진행 중인 요청의 강제 단절, 운영 DNS의 지연, 용량·부하 성능까지 검증한 것은 아니다. `--fresh`를 사용했으므로 과거 장애 데이터 복구를 주장하지 않는다.

## 범위와 고객 안내

상품 API 계약, DB 불변조건, Oracle, 기존 테스트 기대값, 정상 기준 태그는 바꾸지 않았다. 수정은 실습 프록시의 주소 갱신과 관련 회귀 검증에 한정했다.

고객에게는 서버 전환 후 일부 상품 화면이 열리지 않던 연결 경로를 수정했고, 같은 조건에서 상품 목록·상세를 다시 확인했다고 안내할 수 있다. 이 실습 검증과 코드 변경만으로 실제 운영 배포가 완료됐다고 안내하지 않는다.
