# CS-11: 재고가 남아 있는 동시 주문의 500 오류

대상: [이슈 #24](https://github.com/dongho-dev/fault-commerce-lab/issues/24), 기준 브랜치 `incident/cs-11`.

## 원인과 접수 상태

주문은 상품·재고 조회, 배송비 계산, 조건부 재고 UPDATE, 주문 INSERT를 하나의 트랜잭션에서 수행한다. CS-11의 엔진은 `REPEATABLE READ`였다. 조회 기준 시점 이후 다른 주문이 동일 재고 행을 변경·커밋하면, 그 행을 갱신하려는 트랜잭션은 PostgreSQL 오류 `40001 / SerializationFailure`로 중단된다.

실제 재현에서 상품 2번을 1개씩 주문한 두 요청은 모두 재고 2개를 조회했다. 요청 A(`…-0-18`)가 재고를 2 → 1로 줄이고 주문 10번을 커밋했다. 요청 B(`…-0-1`)는 재고가 1개 남았지만 UPDATE에서 실패했다. 식별자 끝 번호는 접수 순위가 아니다.

| 한국 시각, 2026-10-07 | 요청 | 기록 |
| --- | --- | --- |
| 11:14:36.359188 | A | 재고 2개 조회 |
| 11:14:36.362777 | B | 재고 2개 조회 |
| 11:14:36.378178 | A | 재고 2 → 1 갱신 |
| 11:14:36.383653 | A | 주문 10번과 재고 차감 커밋 |
| 11:14:36.450266 | B | 재고 UPDATE의 예외 기록 |

B는 UPDATE의 반환값을 받기 전에 예외가 발생했으므로 `stock_change is None`인 재고 부족 분기에 도달하지 않는다. 트랜잭션은 롤백하고 예외가 미들웨어로 전파되어 `500 INTERNAL_SERVER_ERROR`가 된다. 이번 재현의 실패 DB 트랜잭션들은 모두 롤백됐고, 성공 응답의 주문 ID와 DB 주문 ID가 정확히 일치했다. 실패 주문이 저장되거나 재고만 차감된 흔적은 없었다.

클라이언트와 서버 로그는 요청 ID로 대조했고, DB의 오류·롤백은 DB 세션과 트랜잭션으로 대조했다. DB 로그에 HTTP 요청 ID가 없으므로 개별 요청과 DB 세션을 임의로 일대일 연결하지 않았다. 요청·응답 전송 단절은 재현되지 않았다.

## 선택한 변경

`app/database.py`의 엔진 격리수준을 `READ COMMITTED`로 명시한다. 현재 재고 차감은 `current_stock >= quantity` 조건과 `current_stock - quantity` 계산을 하나의 UPDATE로 수행한다. 다른 갱신을 기다린 뒤 커밋된 최신 행으로 조건을 다시 평가할 수 있으므로, 재고가 있으면 주문을 완료하고 소진됐으면 기존 업무 오류 경로로 409를 반환한다.

재고 차감과 주문 저장의 단일 트랜잭션, API 계약, DB 제약, Oracle과 기존 테스트는 유지한다. 정상 기준 `l1-baseline-v2`도 PostgreSQL 기본 격리수준인 Read Committed를 사용하는 구조다. [PostgreSQL 16 동작 설명](https://www.postgresql.org/docs/16/transaction-iso.html#XACT-READ-COMMITTED)

`SERIALIZABLE`로 상향하면 동시 갱신 중단 가능성이 남는다. 이번 변경에는 재시도 계층, 선착순 큐, 주문 멱등성 확대를 추가하지 않는다. 수량과 주문·재고의 일치가 범위이며, 어떤 요청이 먼저 성공하는지는 보장하지 않는다.

## 검증

재고 10개에 1개씩 동시 주문 20건을 보낸 실제 HTTP 대조 실험:

| 결과 | 변경 전 | Read Committed |
| --- | ---: | ---: |
| 201 주문 성공 | 9 | 10 |
| 409 재고 부족 | 0 | 10 |
| 500 서버 오류 | 11 | 0 |
| 최종 재고 | 1 | 0 |

각 조건의 한 번씩 실행한 관찰이며 실패율 통계가 아니다. 추가한 `test_order_isolation.py`는 재고 조회 후 갱신 전 장벽으로 트랜잭션을 겹치게 해, 요청 타이밍만으로 우연히 통과하는 검증을 피한다. 재고/요청 수 2/2, 1/2, 10/20의 세 경우가 변경 전에는 모두 500으로 실패했고 변경 후 통과했다. DB 결과와 성공 응답의 주문 ID도 대조한다.

- 주문·상품·재고 제약과 실제 HTTP 동시 주문 대상 회귀 검사: **30개 통과**.
- 현재 worktree 코드로 `python -m lab_suite.operator check --expect healthy --fresh`: **통과**.
- 공식 실습의 주문 요청 **128건**에서 응답 계약, 주문 ID 대조, 재고 등식, 부족한 재고, 수량 2개, 혼합 수량의 유효한 처리 순서를 확인했다.
- Ruff 정적 검사와 변경된 DB 설정의 mypy 검사 통과.

[검증 요약과 실행 식별자](evidence/cs-11-verification.json)에 HTTP 결과, 요청 추적, 이미지 ID, 앱 소스 및 원자료 해시를 보존했다.

## 고객 안내와 범위

위 DB 대조로 롤백이 확인된 재현 요청은 최종 접수되지 않았고 재고도 차감하지 않았다. 수정 후 구매 가능한 재고로 다시 주문할 수 있다. 일반적인 500 응답만으로 모든 요청의 미접수를 단정하지 않으며, 과거 요청을 안내할 때는 해당 주문의 최종 DB 상태를 별도로 확인해야 한다.

검증은 격리된 새 임시 DB와 합성 상품을 사용했다. 실제 고객 데이터 복구, 배포, 브라우저 UI 검증이나 엄격한 선착순 보장은 포함하지 않는다.
