## 증상과 원인

같은 검색 조건에 맞는 상품을 1개에서 2개, 다시 3개로 추가했다. 기존 창에서 목록을 다시 열거나 일반 새로고침을 해도 최초 1개만 보였다. 같은 브라우저 프로필의 새 탭과 별도 새 창에서도 같았다. 독립된 브라우저 환경에서는 2개, 3개가 모두 보였다. 따라서 단순히 새 창을 열면 해결된다는 설명은 정확하지 않다.

브라우저는 목록을 재조회할 때 기존 응답의 `ETag`를 `If-None-Match`로 보내 변경 여부를 확인했다. 중계서버는 매 요청마다 앱 서버에서 최신 JSON을 받은 뒤 응답 여부를 결정한다. 변경 확인 요청이 빠지거나 최신 목록을 조회하지 않는 문제가 아니었다.

수정 전 `representation_tag()`는 요청 주소만 해시하고 실제 응답 본문을 사용하지 않았다. 같은 주소라면 상품 내용이 바뀌어도 표식이 같아져 잘못된 `304 Not Modified`를 보냈다. 브라우저는 이에 따라 저장된 응답을 재사용했다.

실측 예시에서 앱 서버가 반환한 본문은 348 → 659 → 970바이트로 바뀌고 본문 해시도 달라졌지만, 중계서버의 `ETag`는 그대로였다. 기존 브라우저로 나간 실제 HTTP 상태는 `304`, 브라우저가 프런트 코드에 제공한 상태는 저장된 응답을 반영한 `200`이었다.

## 어떤 순서로 확인했는가

1. 프런트에서 `route()`가 검색 화면으로 진입하면 `renderListing()` → `listProducts()` → `fetch()`를 호출하는지 확인했다. 목록을 재진입할 때 메모리에 저장한 상품만 바로 그리는 경로가 아니었다.
2. 브라우저가 실제로 전송한 헤더를 확인했다. 기존 환경은 `If-None-Match`를 보냈고, 독립 환경의 첫 조회에는 그 헤더가 없었다.
3. 중계서버가 앱 서버의 조건부 응답을 그대로 전달하는지 확인했다. 목록 요청에서는 조건부 헤더를 제거해 앱 서버에 요청하고, `200` 응답의 본문 전체를 받은 뒤 직접 표식을 비교했다.
4. 같은 요청 주소에 대한 로그를 연결했다. 앱 서버 본문은 1개 → 2개 → 3개로 바뀌었는데 중계서버 표식은 동일했다. `representation_tag(request_target, representation)`가 두 인자를 받지만 실제로는 첫 인자만 사용함을 확인했다.
5. 응답 전송 분기를 확인했다. 표식이 같으면 상태를 `304`로 바꾸고 본문을 보내지 않았다. 브라우저는 저장된 본문을 재사용했으므로 프런트 렌더링 코드는 정상적인 응답처럼 예전 상품을 표시했다.

`Cache-Control: no-cache`는 응답 저장 자체를 금지하는 설정이 아니라, 재사용 전에 서버에 확인하도록 하는 설정이다. 따라서 기존 브라우저가 조건부 요청 후 `304`에 따라 저장된 본문을 쓰는 것은 정상 동작이다. 원인은 변경된 본문에 같은 표식을 부여한 중계서버에 있었다. [HTTP 캐시 규칙](https://www.rfc-editor.org/rfc/rfc9111.html#section-5.2.2.4)

## 선택한 수정

[중계서버](../../lab_suite/cache_gateway.py)의 변경 표식을 요청 주소, 구분 바이트, 실제 응답 본문을 합친 SHA-256으로 계산한다.

1. 브라우저의 상품 목록 요청을 받는다.
2. 앱 서버에서 현재 목록 JSON을 받는다.
3. 요청 주소와 JSON으로 현재 `ETag`를 계산한다.
4. 브라우저가 보낸 표식과 같으면 `304`, 다르면 `200`과 최신 JSON을 보낸다.

새 상품 추가, 가격 변경, 재고 변경처럼 응답 내용이 달라지면 새 본문을 전달한다. 조회 결과가 그대로면 기존 `304` 처리를 유지한다. 수정 전 표식을 보관한 브라우저도 다음 재조회에서 최신 본문을 받을 수 있다.

이 변경은 브라우저에 보내는 본문 재사용 판정을 바로잡는다. 중계서버가 매 요청마다 앱 서버의 전체 응답을 받는 기존 구조는 유지하며, DB 조회량이나 처리 용량을 줄였다는 의미는 아니다.

### 수정 범위를 정한 이유

| 선택지 | 판단 | 이유와 검증 범위 |
| --- | --- | --- |
| 요청 주소와 실제 본문으로 표식 계산 | 적용 | 같은 주소라도 내용이 바뀌면 새 응답을 전달하고, 내용이 같으면 기존 재사용을 유지한다. 실제 구현·회귀·브라우저 검증을 수행했다. |
| 브라우저에서 캐시를 무조건 무시하거나 서버에 `no-store` 설정 | 적용하지 않음 | 브라우저는 이미 변경 여부를 확인하고 있었다. 잘못된 판정을 고치면 기존 캐시 동작을 유지할 수 있으므로 캐시 기능 전체를 없앨 필요가 없었다. 별도 구현·성능 비교는 하지 않았다. |
| 일정 간격의 재조회, TTL 또는 서버 푸시 추가 | 적용하지 않음 | 재조회 자체가 실패하는 것이 원인이어서, 같은 잘못된 판정을 더 자주 요청하는 방식으로 해결할 문제가 아니었다. 실시간 신상품 알림은 이번 완료 조건에 포함하지 않았다. |
| SQL·페이지 분배·프런트 렌더링 변경 | 적용하지 않음 | 같은 조건의 앱 서버 응답과 독립 브라우저에서 최신 목록이 확인됐다. 이번 원인을 해결하는 데 필요하지 않았다. |

위 표의 미적용 대안은 이번 범위 결정을 설명한 것이며, 각각을 구현해 비교 실험했다는 의미가 아니다.

## 최신 정보를 확인하는 시점

고정된 동기화 주기는 없다. 프런트는 목록 최초 진입, 다른 화면에서 목록으로 재진입, 검색 조건·정렬·페이지 변경, 일반 새로고침 시 목록을 조회한다. 이때 브라우저가 변경 여부를 확인하고, 응답이 바뀌었으면 새 목록을 받는다.

화면을 그대로 켜둔 상태에서 자동으로 신상품을 끼워 넣는 기능은 추가하지 않았다. `Cache-Control: no-cache`와 조건부 요청을 유지했으며, 주기적 조회나 서버 푸시도 추가하지 않았다.

## 검증 결과

### 재현 조건과 측정 단위

- 기준 소스는 `5616139bc047126ce5c90232c00cf2aeb65a7c2c`다. 수정 전 진단은 별도 소스 사본, 수정 후 작업은 전용 Git worktree에서 수행했다.
- 각 동작마다 독립된 프로필과 고유 검색어를 사용했다. 앞선 동작에서 받은 응답이 다른 동작의 비교를 오염시키지 않도록 분리했다.
- 각 조건의 최초 상품 A는 12,000원, 다음에 추가한 B는 16,000원, C는 19,000원이었다. 같은 검색 조건·가격 오름차순·첫 페이지·페이지 크기 20으로 비교해 페이지 밖에 밀려나는 경우를 제외했다.
- 상품은 API로 등록하고 목록·상세를 다시 읽었다. DB를 직접 조작해 결과를 만들지 않았다.
- ‘8회’는 **4가지 고객 동작 × 상품 추가 2단계**다. 동시 사용자 수, 초당 요청 수, 부하 시험 결과가 아니다. 대조군 요청과 카테고리 수 조회까지 포함한 전체 HTTP 요청 수도 아니다.
- 기존 검증 이미지의 headless shell에서는 새 탭 요청도 별도 window ID로 생성되어 실제 탭·창 구분을 증명하기 어려웠다. 진단 환경을 보완해 일반 Chromium을 Linux Xvfb에서 실행했다. 이 준비 단계는 상품 증상의 검증 결과로 세지 않았다.
- 브라우저의 캐시를 비활성화하거나 응답을 가로채 바꾸지 않았다. 실제 네트워크 기록과 DOM의 상품 ID·이름·개수, 화면 캡처를 함께 확인했다. 사용자 Windows 데스크톱의 입력은 사용하지 않았다.

회귀 테스트는 실제 로컬 HTTP 서버 사이에서 새 상품, 가격, 재고, 검색 조건별 결과와 정확한 응답 본문을 확인한다. 변경 없는 결과의 정확 일치·약한 표식·표식 목록 처리와 이전 버전 표식도 확인했다. [테스트](../../lab_suite/tests/test_cache_gateway.py)

수정 전 처음 추가한 7개 테스트에서 4개는 새 본문을 가진 `200`을 기대했지만 `304`를 받아 실패했고, 변경 없는 응답의 3개 테스트는 통과했다. 이후 수정 전 표식을 가진 브라우저의 복구를 확인하는 1개 테스트를 더해, 최종 8개가 통과했다. 테스트 기대값을 실제 오류에 맞추거나 Oracle을 수정하지 않았다.

실습의 HTTP·격리 Linux 브라우저 검증과 Oracle이 통과했다(상품 5개, 주문 1건). 같은 프로필의 탭·창 구분은 Linux Xvfb의 일반 Chromium 140.0.7339.16에서 별도로 확인했다. 새 탭은 기존 창과 같은 window ID, 새 창은 다른 window ID이며 브라우저 context는 같다는 것을 검증했다. 이 추가 검증 후 Oracle도 통과했다(상품 17개, 주문 1건).

수정 전 브라우저 기록: `20261007T041119.414338Z-up/window-result.json`. 수정 후 기록: `artifacts/cs-labs/learner-15/20261007T043008.389865Z-check/result.json`, `window-fix-result.json`. 각 실행 폴더에 요청·응답 기록, 화면 캡처, 컨테이너 로그를 보존했다. 수정 후 실행 이미지: `sha256:ce42f329b364872a2d3eeba3b81f1b801f6c2b8629d1021d190f99fa6d2c651e`.

Ruff 검사와 변경 파일 공백 검사를 통과했다. 정상 기준 태그, Oracle 및 기존 테스트, API 계약, DB 불변조건은 수정하지 않았다. 전체 테스트 스위트, 다른 브라우저 엔진, 부하 성능, 실제 운영 배포는 이번 검증 범위에 포함하지 않았다. 검증 브라우저와 이 실습의 컨테이너·네트워크는 종료했다.
