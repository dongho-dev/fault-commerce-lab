# CS-12 재고 차감 해결 기록

관련 이슈: [#25 한정 수량보다 많은 주문이 접수됩니다](https://github.com/dongho-dev/fault-commerce-lab/issues/25)

## 원인과 선택한 처리

주문과 재고 변경은 이미 하나의 트랜잭션에 있었지만, 재고 차감 값은 ORM 객체에 읽어 둔 `inventory.current_stock`으로 파이썬에서 계산했다. 동시 주문이 같은 값을 읽으면 동일한 잔량을 저장해 앞선 차감이 유실됐다. `WHERE current_stock >= quantity` 조건은 유지돼 재고가 음수가 아니어도 초과 판매가 발생했다.

`decrement_if_available()`의 선행 조회를 제거하고, `Inventory.current_stock - quantity`라는 SQL 열 표현식으로 조건 검사와 차감을 DB 현재 행 값에 적용한다. 변경된 행이 없으면 기존 경로가 `409 INSUFFICIENT_STOCK`을 반환하며, 주문 저장 실패 시 차감도 기존 트랜잭션에서 롤백한다.

- 격리 수준은 `READ COMMITTED`로 유지한다. 두 앱 노드의 실제 연결에서도 이를 확인했다.
- 단일 재고 행의 조건부 갱신으로 해결되므로 격리 수준 상향이나 앱 프로세스별 잠금을 추가하지 않는다.
- 서로 다른 주문의 경쟁 문제이므로 멱등성 기능을 추가하지 않는다.
- 확정 순서는 DB의 재고 확보 결과를 따른다. HTTP 접수 순서의 엄격한 FIFO를 보장하는 변경은 아니다.
- 수정된 재고 저장소 코드는 정상 기준 `l1-baseline-v2`와 동일하다. Oracle, 기존 테스트, API 계약, 스키마와 기준 태그는 변경하지 않았다.

## 실제 재현과 수정 후 검증

2026-10-07, 전용 작업 폴더와 `fcl-exercise-12` 임시 PostgreSQL에서 기존 실습 검증기를 실행했다. 같은 DB를 사용하는 앱 두 개에 실제 HTTP 요청을 보냈다. 각 실행은 새 임시 DB를 사용했으며, 전체 112개 요청과 주문·재고·조회 API를 대조했다.

| 검증 조건 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 재고 5개, 1개 주문 8건 동시 실행, 10개 실험군 | 모든 군에서 8건 승인; 잔량 2~4개로 차감 유실 | 모든 군에서 5건 승인·3건 409; 잔량 0 |
| 재고 10개, 2개 주문 8건 | 8건 승인, 16개 판매, 잔량 8 | 5건 승인·3건 409, 10개 판매, 잔량 0 |
| 재고 12개, 수량 1·2·3 혼합 요청 8건 | 8건 승인, 15개 판매, 잔량 10; 합법적인 처리 순서 없음 | 6건 승인·2건 409, 11개 판매, 잔량 1; 합법적인 처리 순서 존재 |
| 각 앱의 순차 주문 대조군 | 5건 승인·3건 409 | 5건 승인·3건 409 |
| 주문·재고 불변조건과 Oracle | 실패 | 통과 |

혼합 수량의 정확한 승인 조합은 경합 순서에 따라 달라질 수 있다. 검증기는 남은 수량에 따른 승인·거절을 설명할 수 있는 처리 순서가 존재하는지와 최종 DB 수량을 확인한다.

기존 회귀 테스트 5개도 별도 `cs12_regression` DB에서 통과했다.

- 정상 주문의 재고 차감과 가격 스냅샷.
- 재고 부족 요청의 주문 미생성과 재고 보존.
- 주문 저장 예외 시 재고 롤백.
- 재고 10개에 동시 주문 40건: 10건 승인·30건 409, 연결 오류 0.
- 두 상품에 동시 주문 50건: 상품별 수량 독립성과 불변조건 유지.

수정 파일의 Ruff 검사와 포맷 검사도 통과했다. pytest 경고 1개는 기존 Starlette의 AnyIO `BlockingPortal` 별칭 폐기 예정 경고다. 전체 테스트 모음은 실행하지 않았다.

## 증거와 범위

[검증 증거 JSON](evidence/12/atomic-stock-fix.json)에 전후 이미지와 소스 해시, 원본 결과 파일의 위치·해시, 실험군별 응답 수와 DB 수량, Oracle 판정, 격리 수준, 회귀 테스트 출력을 기록했다. 상세 요청별 원본은 해당 작업 폴더의 `artifacts/cs-labs/learner-12/`에 보존했다.

기존 장애 데이터의 보정이나 배포는 수행하지 않았다. 이번 검증은 새 임시 DB에서 수정 코드의 동작을 확인한 결과이며, 이미 접수된 주문의 이행 가능성이나 복구 완료를 뜻하지 않는다.
