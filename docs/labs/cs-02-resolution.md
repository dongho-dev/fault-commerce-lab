# CS-02 해결 과정과 고객 대응 기준

대상: 이슈 [#10](https://github.com/dongho-dev/fault-commerce-lab/issues/10). 검증일: 2026-10-06 (Asia/Seoul).

## 문제와 확인한 사실

고객 증상은 주문 실패 안내, 같은 브라우저의 주문내역 부재, 남은 수량 감소였다. 이 세 화면만으로는 주문 미접수나 다른 고객의 구매 여부를 확정할 수 없다.

`incident/cs-02`를 정상 기준 `l1-baseline-v2`와 비교했다. 주문 서비스는 재고 차감 후 첫 번째 `session.begin()`을 종료하고, 두 번째 트랜잭션에서 주문을 저장하도록 분리되어 있었다. 따라서 재고는 이미 커밋된 상태에서 주문 저장만 롤백될 수 있었다.

현재 체크아웃을 빌드한 격리된 PostgreSQL과 Linux Chromium에서 주문을 한 번 요청했다. 기존 실습 장치가 `OrderRepository.create`의 저장 전에 발생시키는 `RuntimeError`를 그대로 사용했다. 수정 전에는 HTTP 500, 해당 상품의 확정 주문 수량 0, 재고 2 → 1, Oracle 불일치를 확인했다.

## 의사결정

| 판단 | 근거와 결정 |
| --- | --- |
| 주문 처리의 원자성 복원 | 재고 차감과 주문 저장을 하나의 `session.begin()`에 넣었다. 실패하면 두 작업이 함께 롤백되어야 한다. 수정 후 주문 서비스는 정상 기준과 일치한다. |
| 멱등성 기능은 추가하지 않음 | 같은 요청의 반복 없이 한 번의 요청으로 증상이 재현된다. 중복 요청 방지는 별도 문제이며 이번 실패의 원인을 고치지 않는다. |
| 동시성 제어 방식은 유지 | 재고 차감의 조건부 UPDATE는 기존 구현을 유지했다. 순차적인 단일 요청에서도 장애가 발생하며, 수정 후 동시 주문 회귀 테스트도 통과했다. |
| 응답이나 화면만으로 미접수 판정하지 않음 | 500·타임아웃·브라우저 주문내역 부재는 DB 주문 부재의 충분한 증거가 아니다. 문의별로 서버 로그와 DB를 대조한다. |
| 자동 보정·재고변동 원장은 추가하지 않음 | 이슈가 요구한 영향 확인 방법과 재주문 안내를 문서화한다. 현재 L1에는 입고·반품·취소 원장이 없고, 이번에 재현한 손상 데이터는 임시 DB였다. 보존 중인 장애 데이터의 보정은 대상과 근거를 정한 별도 작업으로 다룬다. |

[주문 서비스](../../app/services/order.py)의 트랜잭션 경계만 수정했다. 실패 주입 장치와 검증 기대값, Oracle, 기존 테스트, API 계약 및 DB 스키마는 변경하지 않았다.

## 실제 재실행 결과

동일한 저장 실패 조건으로 수정 전후를 각각 빌드하고 새 임시 DB에서 검증했다.

| 단계 | 주문 응답 | 실패 상품의 확정 주문 수량 | 실패 후 재고 | Oracle |
| --- | --- | --- | --- | --- |
| 수정 전 | 500 | 0 | 2 → 1 | 불일치 탐지 |
| 수정 후 | 500 | 0 | 2 → 2 | 통과 |

수정 후 정상 주문 대조군은 201, 주문 수량 1, 재고 2 → 1로 통과했다. 실패 주문이 브라우저 주문내역에 남지 않고 입력 우편번호가 유지되는 검사도 통과했다.

- 수정 전: `python -m lab_suite.operator check --expect fault --fresh` 통과.
- 수정 후: `python -m lab_suite.operator check --expect healthy --fresh` 통과.
- 별도 임시 테스트 DB의 기존 회귀 테스트 5개 통과: 정상 주문/가격 스냅샷, 재고 부족, 주문 저장 예외 롤백, 단일 상품 동시 주문, 두 상품 동시 주문.
- 단일 상품 동시 요청 40건: 성공 10건, 재고 부족 30건, 연결 오류 0건, 잔여 재고 0개.
- 변경 파일 Ruff 검사 및 포맷 검사 통과. pytest에는 Starlette/AnyIO 의존성의 폐기 예정 경고 1건이 있었다.

실행 시각, 앱 이미지 ID, 소스 SHA-256, 전후 probe 원본과 회귀 테스트 출력은 [검증 증거](evidence/02/transaction-fix.json)에 보존했다. 이 문서 보완에서는 앱 코드를 추가 변경하지 않았으며, 이미 통과한 실행 검증을 반복하지 않았다.

## 영향받은 사례 확인 방법

1. 문의의 요청 시각, `request_id`, 상품 ID, 수량, 응답 코드와 확보 가능한 주문 ID를 기록한다. 조사 대상 DB와 코드 버전, 관측 시각도 함께 남긴다. 증거 보존 전에는 `--fresh`, `down`, `oracle.reset`을 실행하지 않는다. 실습 DB는 종료 시 사라진다.
2. 대상 `DATABASE_URL`을 확인한 환경에서 기존 읽기 전용 도구로 상품별 불일치 후보와 주문 집계를 확인한다.

   ```text
   python -m oracle.check --json
   python -m tools.db_snapshot
   ```

   L1의 기준은 `initial_stock - confirmed_quantity = current_stock`이다. 차이가 나면 상품 단위 불일치 후보로 기록한다. 이 결과만으로 특정 고객의 주문 실패나 불일치 원인을 확정하지 않는다. 처리 중인 요청이 끝난 일관된 시점을 기준으로 대조한다.
3. `request_id`에 시각·요청 정보를 함께 대조하여 해당 요청의 완료 로그와 예외 위치를 찾는다. 상세 로그가 보존되어 있다면 `stock_updated`, `order_persisted`, `transaction_completed`를 함께 확인한다. `order_persisted`는 커밋 전 로그이므로 그것만으로 접수를 확정하지 않는다.
4. 확보한 주문 ID는 `orders`에서 직접 확인한다. 추가 후보 조사는 상품·기간에 해당하는 주문 전체를 읽기 전용으로 조회한다. `db_snapshot`의 `recent_orders`는 최근 20건뿐이므로 목록에 없다는 이유로 미접수를 판정하지 않는다.
5. 문의별로 접수 확정, 미접수 확정, 상태 불명 중 하나와 그 근거를 기록한다. 상품별 불일치와 고객별 접수 상태는 별도로 기록한다.

현재 주문 테이블에는 고객 식별자, `request_id` 또는 멱등성 키가 없다. 상품·수량·우편번호·시각이 비슷하다는 이유만으로 특정 고객의 주문이라고 확정할 수 없다. 기본 관측 수준은 `basic`이므로 상세 단계 로그가 없을 수 있으며, 로그 부재도 롤백의 증거가 아니다. 증거가 부족하면 상태 불명으로 남긴다.

## 재주문 안내 기준

| 분류 | 필요한 근거 | 고객 안내 |
| --- | --- | --- |
| 접수 확정 | 해당 요청과 연결된 주문 ID가 DB에 존재하고 상태가 `CONFIRMED`임을 확인 | 접수된 주문 ID와 수량을 안내하고 같은 주문을 다시 요청하지 않도록 한다. |
| 미접수 확정 | 동일 요청이 종료되었고 저장 전 실패 또는 롤백 사실을 확인했으며, DB 확인을 포함해 해당 주문이 커밋되지 않았음을 뒷받침하는 증거가 있음 | 미접수를 안내한다. 수정 적용과 해당 상품의 현재 재고 정합성·판매 가능 수량을 확인한 뒤 재주문을 안내한다. |
| 상태 불명 | 타임아웃, 응답 유실, 로그 누락, 요청과 주문의 연결 불가 등으로 커밋 여부를 확정하지 못함 | 접수 여부를 확인 중이라고 안내하고 재주문을 보류한다. 주문 증거를 추가로 확보해 재분류한다. |

HTTP 500, 빈 브라우저 주문내역, 남은 수량 변화만으로 재주문을 권하지 않는다. 이 시스템의 주문 API에는 중복 요청 방지 기능이 없으므로 상태가 불명확할 때 자동 재시도하지 않는다.

## 완료 범위와 남은 조건

코드 수정과 새 임시 DB의 재발 방지 검증, 영향 확인 및 고객 안내 절차를 완료했다. 전체 저장소 테스트 모음은 실행하지 않았다. 자동 브라우저 검증은 Linux 컨테이너 안에서 수행했고, 이번 테스트의 임시 환경은 종료했다.

보존 중인 장애 데이터가 발견되면 코드 수정만으로 해당 재고가 자동 복구되지는 않는다. 그 경우 상품별 불일치와 근거를 보존하고 보정 대상·실행 담당·검증 방법을 별도로 정한다. 이번 PR에는 데이터 보정 스크립트, 재고변동 원장, 멱등성 기능을 포함하지 않으며, 과거 데이터 복구 성공을 주장하지 않는다.
