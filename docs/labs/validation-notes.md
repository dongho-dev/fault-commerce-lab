# 재현 조건과 검증의 한계

사례 04의 중간 실행은 아래처럼 구분한다. 최종 완료 여부는 [검증 기록](verification.md)의 정상·장애·원복 세 단계 결과를 따른다. 통과한 단계만 서로 다른 실행에서 조합하지 않는다.

- 일반적인 짧은 검색 입력 4,000개에서는 메모리 증가를 관측했지만 OOM이나 상품 조회 중단에 이르지 않았다.
- 48,000바이트 진단 문자열을 붙인 합성 URL로 누적을 가속했다. 같은 URL을 반복하는 대조군에도 같은 크기를 적용한다. 이 실험은 운영 트래픽이나 장애 발생 시간을 추정하는 용도가 아니다.
- Docker 기본 swap 조건에서는 RAM이 한도 가까이 증가했어도 OOM이 발생하지 않았다. 이후 사례 04의 정상·장애·원복 모두 RAM 512MB, 추가 swap 없음으로 고정했다. CPU는 기존 기준인 1개다.
- `verification-04-noswap`에서 실제 OOM·고객 조회 실패·재시작 후 회복은 확인됐지만, 원복 단계의 합성 부하 요청 24,000개 중 1개가 연결 종료 오류로 실패했다. 고객 목록·상세 조회 오류와 재시작은 없었다. 이 실행 전체를 완료로 집계하지 않았다.
- 해당 단건 연결 종료의 원인은 확정하지 않았다. 최종 검증에서는 합성 부하 클라이언트의 연결 재사용을 끄고 세 단계를 동일 조건으로 다시 실행했다. 요청 오류를 허용하거나 재시도로 숨기지 않으며, 정상 판정은 모든 요청의 성공을 요구한다.

장애 단계의 통과는 결함이 해결됐다는 뜻이 아니라 의도한 증상이 관측됐다는 뜻이다. 원복 단계는 새 임시 DB에서 정상 소스를 실행한 대조 검증이다. 과거 장애 데이터의 복구를 검증한 것으로 해석하지 않는다.

사례 09는 실제 이미지 교체 중 열린 탭과 새 탭을 비교했다. 사례 10은 Linux Chromium의 접근성 트리와 Tab·Enter 조작을 확인했으며, NVDA 음성 청취는 수행하지 않았다.

최종 `verification-04-connections`에서는 정상·원복 각각 합성 요청 24,000개와 별도 상품 조회가 모두 성공했다. 장애 단계에서는 Docker OOM 1회, 상품 조회 실패 72건, 재시작 1회와 이후 정상 조회 회복을 확인했다. 이 세 단계가 함께 통과한 실행을 최종 근거로 사용한다.
