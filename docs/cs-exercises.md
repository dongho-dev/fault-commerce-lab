# Fault Commerce Lab — 종합 장애 조사 문제 10개

작성일: 2026-10-06 · 출제: gpt-6-astra / xhigh 에이전트 3명 분담 · 통합 검토: Codex

이슈 #1의 ‘고객 문의 → CS팀 확인 사항 → 조사 요청’ 형식을 따른 새 문제 10개입니다. 기존 이슈 #1과 #3은 이 문제집의 개수에 포함하지 않습니다. 문제 번호는 이 문서 안에서 사용합니다.

각 문제는 중심 분야 하나와 여러 연관 분야를 함께 조사하는 종합형으로 구성했습니다. 한 실습에 주입할 주된 결함은 하나입니다. 고객 문의와 CS팀 확인 사항은 모두 출제용 가정이며, 현재 서비스에서 관측한 사고 기록이 아닙니다.

**현재 검증 완료: 10/10. 상세 상태와 검증 범위는 [검증 기록](labs/verification.md)을 따릅니다.**

## 진행 기준

- 정상 기준은 `l1-baseline-v2`이며, 새 incident 브랜치는 이 태그에서 시작합니다. 기준 태그를 이동하지 않습니다.
- 각 문제는 독립된 환경과 데이터로 진행합니다. 서로 다른 문제의 결함을 한 환경에 겹쳐 넣지 않습니다.
- `oracle/`, Oracle 관련 테스트, API 계약, DB 불변조건을 유지합니다. 테스트 기대값을 오류에 맞추거나 DB를 직접 덮어써 정상처럼 만들지 않습니다.
- 정상 API로 합성 상품과 주문을 준비합니다. 실제 결제·회원·인증·환불 기능은 실습 범위에 포함하지 않습니다. 장바구니와 주문내역은 브라우저에 저장되는 현재 구현의 범위를 따릅니다.
- 기본 환경은 앱 CPU 1개·메모리 512MB·워커 1개입니다. 성능 비교가 필요한 경우 같은 데이터·서버 크기·요청 조건을 사용하고, 관련 SLO는 용량 기준 문서를 따릅니다.
- 별도 프록시나 다중 앱이 필요한 문제는 아래 준비 전제대로 정상 환경부터 검증합니다. 추가 토폴로지의 측정값은 기본 단일 앱 수치와 구분합니다.
- 브라우저 검증은 사용자의 화면 잠금·커서 캡처·Pointer Lock 없이 수행합니다. 실제 사용자 경험 확인과 자동 검사 결과를 구분해 기록합니다.

문제를 풀 때는 재현 조건, 확인된 사실과 가설, 원인을 뒷받침하는 비교 실험, 수정 범위, 영향받은 경로의 회귀 검증, 고객 안내를 제출합니다. 정상 복구와 이미 생긴 데이터 영향의 처리는 구분합니다.

참고: [이슈 #1](https://github.com/dongho-dev/fault-commerce-lab/issues/1) · [정상 기준의 용량 문서](https://github.com/dongho-dev/fault-commerce-lab/blob/l1-baseline-v2/docs/capacity-baseline.md)

| 07 | 동시성·비동기 프로그래밍 | 네트워크 지연, UI 상태, 회귀 검증 | 검색어를 바꿨는데 잠시 뒤 이전 상품들이 다시 나옵니다 | 중상 |

| 09 | 소프트웨어공학·빌드와 배포 | 컨테이너, HTTP 자원, 상태 확인 | 새로 접속하면 상단 메뉴만 보이고 상품이 나오지 않습니다 | 중상 |
| 10 | 인간컴퓨터상호작용·접근성 | 접근성 이름, 상품 식별, 기능 검증 | 소리로 들으면 어느 상품의 담기 버튼인지 구분할 수 없습니다 | 중간 |

선택표의 분야는 출제 분류입니다. 조사자에게는 아래에서 선택한 문제의 ‘공개 문제 본문’을 전달하면 됩니다. 구현 위치와 정답은 본문에 포함하지 않았습니다.

## 실습 준비 전제

- **문제 01:** 기존 단일 앱·DB 환경. 여러 페이지를 구성할 합성 상품이 필요합니다.
- **문제 02:** 기존 단일 앱·DB 환경에 통제된 실패 조건을 제공하는 검증 장치가 필요합니다. 정상 기준과 실습 버전에 동일한 조건을 적용합니다.
- **문제 03:** 기존 브라우저·API·DB 환경. 다른 배송비 조건과 비교할 합성 주문 입력을 준비합니다.
- **문제 04:** 기존 고정 크기의 앱·DB 환경. 격리된 장시간 요청 실행기와 자원 관찰이 필요합니다. 재현에 필요한 요청량과 시간은 준비 단계에서 확인합니다.
- **문제 05:** 추가 구성 필요: 동일 앱의 직접 접속 경로와 격리된 테스트 프록시 경로. 두 정상 경로의 동등성을 먼저 확인하고 실습합니다. 현재 기본 구성에 이미 두 경로가 있다는 가정은 하지 않습니다.
- **문제 06:** 추가 구성 필요: 동일한 정상 기준의 앱 2개, 공용 PostgreSQL, 하나의 접속 주소와 각 앱의 비교 경로. 초기화는 한 번 수행하고 연결 수·자원 여유를 확보해 환경을 검증합니다. 단일 앱의 용량 수치와 구분합니다.
- **문제 07:** 기존 앱과 브라우저. 합성 상품 및 요청별 응답 완료 순서를 제어할 검증 환경이 필요합니다.
- **문제 08:** 기존 앱·브라우저와 격리된 합성 상품 데이터. 재현은 로컬 화면의 무해한 표식으로 확인합니다.
- **문제 09:** 실제 컨테이너 빌드·실행 환경. 배포 전부터 열린 탭과 새 브라우저 컨텍스트를 구분합니다.
- **문제 10:** 브라우저 접근성 트리 확인과 실제 화면 낭독기 검증을 구분합니다. 실제 검증에 사용한 브라우저·보조기술 환경을 기록합니다.

실행 도구가 문제별 구성을 준비합니다. 검증 완료 여부는 검증 기록을 기준으로 확인하고, 각 문제는 독립된 환경에서 진행합니다.

## 공개 문제 본문

### 문제 01. 낮은가격순인데 다음 페이지에서 더 저렴한 상품이 나옵니다

> 학습용 가상 VOC입니다. 아래 문의와 확인 사항은 출제를 위한 상황 설정입니다.

**CS팀 VOC 요약**

가격을 비교하려고 검색 결과에서 ‘낮은가격순’을 선택한 고객들이 상품 순서를 믿기 어렵다는 문의를 주셨습니다. 첫 화면에서는 가격이 낮은 상품부터 보이는 것 같지만, 다음 페이지로 넘어가면 앞에서 본 상품보다 저렴한 상품이 다시 나온다는 내용입니다.

**고객 문의**

1. “저렴한 것부터 보려고 낮은가격순을 눌렀어요. 첫 페이지를 다 보고 다음으로 넘어갔는데 더 싼 상품이 있네요.”
2. “검색어도 그대로고 낮은가격순 표시도 그대로예요. 페이지를 넘길 때마다 다시 비교해야 하나요?”
3. “페이지 안에서는 가격이 올라가는 것 같은데, 전체 상품 중 가장 싼 게 처음에 나오는 건 아닌 것 같아요.”
4. “상품을 눌러 들어가도 가격은 목록에서 본 금액과 같아요. 어떤 순서로 보고 있는 건지 궁금합니다.”

**CS팀 확인 사항**

- 제출된 화면에서는 페이지 이동 후에도 검색어·카테고리·정렬 선택 표시가 유지됩니다.
- 문의는 결과가 여러 페이지인 목록에 관한 것입니다. 결과가 한 페이지인 경우에도 문제가 있는지는 확인하지 못했습니다.
- 목록과 상세 화면의 상품 가격은 같습니다. 문의 도중 상품이 새로 등록되었는지는 확인하지 못했습니다.
- 화면 자료만 확보했습니다. 목록 응답과 화면 표시 중 어느 단계에서 순서가 달라지는지는 확인하지 못했습니다.

**요청**

같은 검색 조건에서 페이지를 이동하며 가격을 비교할 수 있는지 조사해 주세요. 영향받는 검색·카테고리·정렬 조건을 확인하고 정상 순서를 복구한 뒤, 고객에게 어떤 결과를 기준으로 상품을 비교하면 되는지 안내할 내용을 정리해 주세요.

### 문제 02. 주문하지 못했다는 안내 뒤에 남은 수량이 줄어 보입니다

> 학습용 가상 VOC입니다. 아래 문의와 확인 사항은 출제를 위한 상황 설정입니다.

**CS팀 VOC 요약**

주문을 완료하지 못했다는 안내를 받은 고객이 상품 화면으로 돌아갔을 때 남은 수량이 줄어 보였다는 문의입니다. 같은 브라우저의 주문내역에서는 해당 주문을 찾지 못했다고 하며, 주문이 접수된 것인지 다시 시도해도 되는지 안내를 요청하고 있습니다.

**고객 문의**

1. “두 개 남았다고 해서 하나 주문했는데 주문하지 못했다고 나왔어요. 돌아가 보니 하나만 남았다고 보여요.”
2. “같은 브라우저에서 주문내역을 열어 봤는데 방금 주문한 상품이 없어요. 제 주문이 들어간 건가요?”
3. “주문이 안 됐으면 다시 누르고 싶은데, 이미 접수된 건데 한 번 더 주문하게 될까 봐 기다리고 있어요.”
4. “장바구니에는 상품이 그대로 남아 있어요. 주문내역이랑 남은 수량 중 무엇을 보고 판단해야 하나요?”

**CS팀 확인 사항**

- 접수 자료에는 주문 실패 안내와 이후 상품 화면의 남은 수량이 포함되어 있습니다. 두 화면 사이에 다른 고객이 주문했는지는 확인하지 못했습니다.
- 고객은 같은 브라우저의 주문내역에서 해당 주문을 찾지 못했습니다. 서버에 주문이 저장되었는지는 아직 확인하지 못했습니다.
- 일부 문의에는 오류 화면의 요청 식별자가 첨부되어 있습니다. 화면 자료만으로 최종 주문 접수 상태를 확인하지 못했습니다.
- 상품 목록과 상세 화면은 계속 열립니다. 모든 상품·모든 주문에서 발생하는지는 확인하지 못했습니다.

**요청**

문의별 최종 주문 접수 상태와 남은 수량의 변화를 함께 조사해 주세요. 문제를 복구하고, 이미 영향을 받은 사례의 확인 방법과 재주문 안내 기준을 제시해 주세요. 조사 중 확정하지 못한 상태도 구분해서 알려 주세요.

### 문제 03. 주문하기 전과 주문완료 화면의 배송비가 다릅니다

> 학습용 가상 VOC입니다. 아래 문의와 확인 사항은 출제를 위한 상황 설정입니다.

**CS팀 VOC 요약**

주문 화면에서 확인한 배송비보다 주문완료 화면의 배송비가 더 높다는 문의가 접수되었습니다. 고객들은 주문 중 상품과 수량을 바꾸지 않았다고 하며, 다음 주문에서는 어느 금액을 기준으로 판단하면 되는지 설명을 요청하고 있습니다.

**고객 문의**

1. “서울 강남 우편번호 06236을 넣었어요. 주문하기 전에는 배송비가 3,000원이었는데 완료 화면에는 5,500원으로 나와요.”
2. “상품도 하나고 수량도 하나예요. 주문 버튼을 누르기 전후로 바꾼 게 없는데 총금액이 달라졌어요.”
3. “완료 화면에 적힌 우편번호는 제가 넣은 것과 같아요. 주소를 잘못 입력한 것도 아닌데 왜 배송비가 붙었는지 모르겠어요.”
4. “주문내역에도 더 높은 금액으로 보여요. 앞으로는 주문하기 전에 보이는 금액을 믿어도 되나요?”

**CS팀 확인 사항**

- 해당 문의는 상품금액이 20만 원 미만이고 수량이 1개인 주문에 관한 것입니다.
- 주문 전후 화면에 표시된 상품·수량·우편번호는 같습니다.
- 주문 전후 배송비가 같은 사례도 있습니다. 어느 입력 조건에서 차이가 생기는지는 아직 확정하지 못했습니다.
- 이 실습 쇼핑몰은 실제 결제를 하지 않습니다. 확인 대상은 예상 금액과 접수된 주문 금액입니다.

**요청**

주문 전후 금액이 달라지는 조건과 영향받는 주문을 조사해 주세요. 배송비와 주문 총액이 일관되게 표시·기록되도록 복구하고, 기존 주문의 금액을 확인할 때 사용할 기준과 고객 안내문을 정리해 주세요.

### 문제 04. 한동안 정상 이용하던 쇼핑몰이 하루 중 몇 차례 함께 열리지 않습니다

**요청**

### 문제 05. 같은 쇼핑몰인데 접속 주소에 따라 상품 목록이 열리지 않습니다

> 학습용 가상 VOC입니다. 아래 문의와 확인 사항은 출제를 위한 상황 설정입니다.

**CS팀 VOC 요약**

고객에게 안내된 접속 주소에서는 전체 상품이나 검색 결과가 많은 화면을 불러오지 못하지만, CS가 안내한 점검용 주소에서는 같은 화면을 이용할 수 있다는 문의입니다. 문제가 있는 주소에서도 메뉴와 이미지, 일부 상품 상세는 정상적으로 보였습니다. 검색어를 구체적으로 입력하면 정상 이용이 가능했다는 제보도 있습니다.

**고객 문의**

1. “평소 쓰던 주소에서 전체 상품을 누르면 오류가 나요. 상담 중 받은 주소에서는 같은 상품들이 나옵니다.”

- 문제 경로에서도 메뉴와 정적 이미지가 표시된 사례가 있습니다.
- 상품 상세와 결과가 적은 검색은 정상이라는 제보가 있습니다. 정확한 성공·실패 경계는 아직 정리하지 못했습니다.

- 문의 시점의 상태 점검은 정상이었으며, 앱 쪽 기록에는 일부 해당 조회가 성공으로 남아 있습니다. 고객 화면의 실패와 기록이 다른 이유는 조사하지 않았습니다.

**요청**

접속 경로와 요청 조건을 비교하여 실패 범위를 확정하고, 앱의 처리 기록과 고객이 받은 결과가 다른 이유를 조사해 주세요. 정상적인 상품 조회를 복구한 뒤 큰 목록과 작은 조회 모두에서 확인해 주세요. 고객에게는 확인된 임시 이용 경로와 복구 상황을 안내해 주세요.

### 문제 06. 같은 상품의 재고가 새로고침할 때마다 이전 숫자로 돌아옵니다

> 학습용 가상 VOC입니다. 아래 문의와 확인 사항은 출제를 위한 상황 설정입니다.

**CS팀 VOC 요약**

주문을 마친 뒤 같은 상품 상세를 다시 열었을 때 재고가 줄어든 숫자와 이전 숫자로 번갈아 표시된다는 문의입니다. 상품명과 가격은 같았으며, 고객이 연속 주문을 하거나 여러 화면을 빠르게 이동한 상황은 아니었습니다. 주문 완료 화면에는 주문번호가 표시되어 있어 고객은 재고 표시와 주문 접수 중 어느 쪽을 믿어야 할지 혼란을 겪고 있습니다.

**고객 문의**

1. “5개 남아 있는 상품을 1개 주문했어요. 다시 보니 4개였는데 새로고침하니까 다시 5개라고 나옵니다.”
2. “화면이 다 열린 다음에 다시 눌렀는데도 숫자가 달라져요. 상품 이름과 가격은 그대로입니다.”
3. “친구한테 같은 상품 링크를 보냈는데 저는 4개, 친구는 5개로 보여요.”
4. “주문 완료 화면에서 주문번호까지 받았는데 재고가 다시 늘어서 주문이 취소된 건지 모르겠어요.”
5. “뒤로 가기만 잘못된 건가 해서 새 창에서도 열어 봤는데, 거기서도 두 숫자가 번갈아 보여요.”

**CS팀 확인 사항**

- 비교한 화면은 같은 상품의 상세 화면이며, 상품명·가격의 차이는 제보되지 않았습니다.
- 고객은 각 화면의 로딩을 기다린 뒤 순서대로 새로고침했다고 설명했습니다.
- 재고 차이는 주문 완료 이후에 제보되었습니다. 두 숫자 중 어느 쪽이 현재 판매 가능한 수량인지는 확인하지 않았습니다.
- 고객에게 주문번호가 표시된 것은 확인했지만, 화면 표시만으로 서버의 주문·재고 상태가 일치한다고 판단하지 않았습니다.
- 새 창과 다른 기기에서도 차이가 있었다는 제보가 있습니다. 영향을 받는 상품 범위와 지속 시간은 아직 모릅니다.

**요청**

같은 상품에서 서로 다른 재고가 표시되는 조건을 조사하고, 주문의 실제 접수 여부와 재고 상태를 구분하여 확인해 주세요. 고객이 새로 조회한 재고를 신뢰할 수 있도록 복구하고, 정상 주문 이후에도 조회 결과가 일관되는지 검증해 주세요. 고객에게는 확인된 주문 상태와 표시 오류의 영향을 구분해 안내해 주세요.

### 문제 07. 검색어를 바꿨는데 잠시 뒤 이전 상품들이 다시 나옵니다

**CS팀 VOC 요약**

상품을 연달아 검색하면 화면에 적힌 검색어와 실제 상품 목록이 달라진다는 문의가 있습니다. 고객은 새 검색 결과를 보고 있던 중 앞서 찾았던 상품이 다시 나타나 어떤 결과를 선택해야 할지 혼란스럽다고 합니다.

**고객 문의**

1. “기타 카테고리에서 ‘여행 파우치’를 찾다가 바로 ‘케이블 정리함’으로 바꿨어요. 정리함이 나왔는데 조금 뒤에 파우치 목록으로 돌아갔어요.”
2. “검색창이랑 결과 제목에는 정리함이라고 적혀 있는데 아래에는 파우치가 있어요. 제가 검색어를 잘못 넣은 건 아닌 것 같아요.”
3. “상품이 다 나올 때까지 기다렸다가 다음 검색을 하면 괜찮아요. 처음 검색이 오래 걸려서 다른 걸 찾을 때 자주 이래요.”

- 검색을 연달아 진행했을 때 발생합니다. 모든 접속 환경에서 발생하는지는 확인하지 못했습니다.
- 현재 문의 범위는 검색 결과입니다. 주문내역이나 재고의 이상 여부까지 확인한 상황은 아닙니다.

**요청**

발생 조건과 영향을 조사하고, 마지막으로 선택한 검색 조건에 맞는 결과를 안정적으로 확인할 수 있도록 복구해 주세요. 복구 전 고객이 사용할 수 있는 임시 이용 방법과 복구 후 확인 방법도 CS팀에 전달해 주세요.

### 문제 09. 새로 접속하면 상단 메뉴만 보이고 상품이 나오지 않습니다

**CS팀 확인 사항**

- 업데이트 후 처음 접속한 브라우저에서 상품 영역이 비어 있는 현상이 반복됩니다.
- 로고·검색창·하단 안내는 보입니다. 사이트에 완전히 접속할 수 없는 상태와는 구분됩니다.
- 업데이트 전부터 열어 둔 화면에서 상품 검색을 계속한 사례가 있습니다. 그 화면을 다시 열었을 때도 정상인지는 확인하지 못했습니다.
- 서비스 상태 확인 화면에서는 정상으로 표시됩니다. 고객이 보는 첫 화면까지 정상인지 확인한 결과는 아닙니다.

**요청**

접속 시점과 화면 상태에 따른 차이를 조사하고 새로 방문한 고객도 쇼핑몰을 사용할 수 있도록 복구해 주세요. 정상 복구를 확인할 항목과 고객에게 전달할 이용 재개 안내를 정리해 주세요.

### 문제 10. 소리로 들으면 어느 상품의 담기 버튼인지 구분할 수 없습니다

> 학습용 가상 VOC입니다. 아래 문의와 확인 사항은 출제를 위한 상황 설정입니다.

**CS팀 VOC 요약**

화면 낭독 기능으로 상품 목록을 이용하는 고객이 담기 버튼만 탐색할 때 상품을 구분할 수 없다는 문의입니다. 버튼은 작동하지만 어떤 상품을 담는지 확신하기 어려워 구매 준비 과정에서 반복적인 확인이 필요하다고 합니다.

**고객 문의**

1. “상품 목록에서 버튼을 하나씩 듣고 있는데 전부 ‘장바구니 담기’라고만 나와요. 지금 어느 상품 버튼인지 모르겠어요.”
2. “키보드로 버튼까지 이동해서 누르면 상품은 들어가요. 그런데 원하는 상품이었는지 장바구니에 가서 다시 확인해야 해요.”
3. “옆 사람은 상품 사진 아래 버튼을 보고 구분하던데 저는 버튼만 들으면 다 같아요. 상품 이름도 함께 알 수 있으면 좋겠어요.”

**CS팀 확인 사항**

- 화면 낭독 기능으로 상품 목록의 버튼을 차례로 탐색할 때 발생합니다.
- 서로 다른 상품의 담기 버튼이 모두 같은 이름으로 안내됩니다.
- 버튼으로 이동하거나 실행하는 동작 자체의 실패는 제보되지 않았습니다. 마우스로 상품 카드를 보고 선택한 경우에는 구분할 수 있습니다.
- 현재 확인 범위는 상품 목록의 담기 버튼입니다. 모든 보조기술과 전체 구매 과정의 접근성을 검증한 상황은 아닙니다.

**요청**

화면 낭독으로 상품별 담기 버튼을 구분할 수 없는 원인을 조사하고 복구해 주세요. 해당 이용 방식으로 상품을 선택하고 담는 과정을 확인한 뒤, 검증한 환경과 고객 안내 내용을 CS팀에 전달해 주세요.
