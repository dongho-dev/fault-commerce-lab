# 용량 기준 (l1-baseline-v2)

정상 시스템이 어느 정도의 트래픽을 목표 품질 안에서 처리하는지 기록한 기준표입니다.
트래픽 장애를 조사할 때는 이 표와 비교해 "평소와 무엇이 달라졌는지"를 판단합니다.

## 서버 크기 (고정)

| 항목 | 값 | 설정 |
| --- | --- | --- |
| 앱 CPU | 1개 | `APP_CPUS=1.0` |
| 앱 메모리 | 512MB | `APP_MEMORY=512m` |
| Uvicorn 워커 | 1개 | `UVICORN_WORKERS=1` |
| DB 커넥션 풀 | 30 + overflow 30 | `DATABASE_POOL_SIZE`, `DATABASE_MAX_OVERFLOW` |
| PostgreSQL | 16, 자원 제한 없음, `max_connections` 기본값 100 | |

스케일 업은 위 값(CPU, 워커)을 늘리는 것이고, 스케일 아웃은 앱 인스턴스를 늘리고 앞에
로드밸런서를 두는 것입니다. 앱 한 대가 DB 커넥션을 최대 60개 쓰므로, 인스턴스를 늘릴 때는
PostgreSQL `max_connections`(100)를 함께 고려해야 합니다.

## 목표 품질 (SLO)

| 지표 | 목표 |
| --- | --- |
| p95 응답 시간 | 300ms 이하 |
| p99 응답 시간 | 1,000ms 이하 |
| 에러율 (5xx, 타임아웃, 409 외 4xx) | 1% 미만 |

`409 INSUFFICIENT_STOCK`은 정상적인 업무 결과이므로 에러로 세지 않습니다.

## 부하 모델

`scripts/load_test.py`가 가상 사용자(VU)를 단계별로 늘리며 측정합니다. 각 가상 사용자는
아래 비율로 행동을 고르고, 행동 사이에 평균 100ms를 쉽니다.

| 행동 | 비율 | 요청 |
| --- | --- | --- |
| 카테고리·할인 목록 | 30% | `GET /products?category=…` / `?sort=discount` |
| 검색 | 15% | `GET /products?q=…` |
| 상품 상세 | 35% | `GET /products/{id}` |
| 주문 | 20% | `POST /orders` (그중 10%는 품절 상품) |

주문은 부하 테스트가 만든 재고 1,000,000개짜리 전용 상품 20개에 분산됩니다.

```bash
make load
make load LOAD_ARGS="--stages 10,20,40 --stage-seconds 60 --label after-fix"
```

결과는 `artifacts/load-<label>.json`에 저장됩니다.
