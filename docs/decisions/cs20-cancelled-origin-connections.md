# CS-20: 취소된 원 서버 연결의 재사용 방지

- 이슈: [#34](https://github.com/dongho-dev/fault-commerce-lab/issues/34)
- 대상: `incident/cs-20`, 진단 기준 커밋 `fa1bba0659fd34ef912c9ed02ea248f23b08a5ba`

## 원인과 관측

클라이언트가 상품 A 조회를 취소하면 게이트웨이는 원 서버 응답을 읽던 작업을 취소한다. `OriginPool.exchange()`의 `complete`는 응답 전체를 읽기 전에는 `False`이며, 읽기가 끝나면 응답의 재사용 가능 여부를 받는다. 그러나 `release()`가 이 값을 무시하고 `reusable = True`로 처리해, A 응답이 미완료인 연결을 풀에 돌려주었다. 다음 B 요청이 같은 연결을 사용하면서 A 응답을 B의 결과로 읽었다.

실제 PostgreSQL 조회를 잠금으로 대기시킨 뒤 테스트 클라이언트 연결을 끊는 조건으로 재현했다. 유휴 시간 만료를 재현한 것은 아니다. 원 서버 직접 조회와 DB 상품·재고는 정상이었고, 게이트웨이 경유 응답은 HTTP 200이면서 다른 상품의 전체 JSON을 담았다.

| 요청 | 수정 전 | 수정 후 |
| --- | --- | --- |
| 정리함, 상품 2 | 파우치, 상품 1, 12,000원 | 정리함, 상품 2, 17,000원 |
| 텀블러, 상품 3 | 정리함, 상품 2, 17,000원 | 텀블러, 상품 3, 23,000원 |
| 없는 상품 | 상품 3을 HTTP 200으로 반환 | HTTP 404, `PRODUCT_NOT_FOUND` |

수정 전에는 취소된 A와 후속 B가 연결 번호 1을 공유했다. 수정 후에는 A가 연결 1, B가 새 연결 2를 사용했다.

## 선택한 변경과 범위

`lab_suite/round2_c_gateway.py`의 `OriginPool.release()`에서 `reusable`을 전달받은 `complete` 값으로 결정한다. 응답 읽기가 취소되거나 실패한 연결과 `Connection: close` 응답을 받은 연결은 닫고, 끝까지 읽은 재사용 가능 연결만 풀에 반환한다. 취소된 응답을 추가로 기다리지 않으므로 후속 요청이 A 처리 완료에 묶이지 않는다. 정상 응답 이후의 연결 재사용은 유지한다.

프론트 상품 표시 로직, API 계약, Oracle, DB 불변조건, 기존 검증 기준과 정상 기준 태그는 변경하지 않는다. 취소된 원 서버의 SQL 작업을 중단하는 기능은 추가하지 않는다.

## 검증

- 실제 TCP 회귀 테스트를 추가했다. 헤더 수신 전 취소, 일부 본문 전송 후 취소, 정상 연결 재사용, 서버의 연결 종료 지시를 다룬다. 기존 코드에서 3개 실패·1개 통과, 수정 후 4개 모두 통과했다.
- 기존 HTTP 응답 경계 검사 5개를 함께 실행해 총 9개 통과했다. 전체 저장소 테스트와 다른 CS 사례는 실행하지 않았다.
- 수정 파일 2개의 Ruff 검사 통과.
- 기존 CS-20 검증기를 `python -m lab_suite.operator check --expect healthy --fresh`로 실행해 `passed=true`, `healthy=true`를 확인했다. 원 서버·고객 경로 대조 9건의 전체 JSON이 일치했고, 실제 Linux Chromium에서 정리함과 텀블러의 이름·가격·상품번호를 확인했다. 페이지 오류는 없고 DB 전후 상태도 동일했다.
