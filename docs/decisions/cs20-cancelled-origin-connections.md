# CS-20: 취소된 원 서버 연결의 재사용 방지

- 이슈: [#34](https://github.com/dongho-dev/fault-commerce-lab/issues/34)
- PR: [#40](https://github.com/dongho-dev/fault-commerce-lab/pull/40), 대상 `incident/cs-20`
- 장애 소스: `fa1bba0659fd34ef912c9ed02ea248f23b08a5ba`
- 구현·회귀 테스트 커밋: `75129ceb8d86178a4a1140d38c786522ff5596b9`

상품 A 조회를 취소한 뒤 상품 B를 열면 A의 이름·가격이 표시됐다. 게이트웨이가 A 응답을 끝까지 읽지 않은 원 서버 연결을 풀에 돌려주었고, B 요청이 그 연결에서 A 응답을 읽는 것이 원인이었다. 연결 반환 시 기존에 계산한 재사용 가능 여부를 따르도록 수정했다. 같은 취소 조건에서 실제 API와 브라우저의 상품 일치를 확인했다.

이 문서는 CS-20에 관한 대화와 의사결정의 요약이다. 같은 채팅에서 먼저 다룬 CS-14의 DB 연결 상속 문제는 별개다. 아래에서 A는 파우치, B는 정리함, C는 텀블러다.

## 실제 재현 조건과 증거 순서

진단과 수정 검증은 별도 작업 폴더의 CS-20 전용 Linux 컨테이너에서 수행했다. 원래 실행 중인 기본 쇼핑몰 환경은 사용하지 않았다. 공통 검증기와 판정 기준은 변경하지 않았다.

1. 실습의 상품 생성 API로 A·B·C를 만든다. ID는 각각 1·2·3, 가격은 12,000·17,000·23,000원, 초기·현재 재고는 각각 7개다. 상품명의 실행별 식별자는 두 실행에서 다르다.
2. 원 서버 직접 경로 3건과 고객 게이트웨이 경로 3건의 응답을 해당 실행의 생성 결과와 비교한다. 최초 대조군은 모두 정상이다.
3. PostgreSQL 테이블 잠금으로 A의 실제 조회를 대기시키고 `pg_stat_activity`에서 잠금 대기를 확인한다. 응답 데이터를 조작하는 방식은 아니다.
4. 별도의 TCP 테스트 클라이언트로 A를 요청하고, 게이트웨이의 전송 이벤트와 실제 DB 대기를 확인한 뒤 그 클라이언트 연결을 닫는다. 브라우저가 A 요청을 자동 취소했다고 가정하지 않는다.
5. 게이트웨이의 취소 이벤트를 확인한 뒤 Linux Chromium에서 B 상세 화면으로 이동한다. B 요청이 원 서버 연결로 전송된 것을 확인하고 잠금을 해제한다.
6. B 요청의 HTTP 상태·전체 JSON·헤더와 브라우저 화면을 기록한다. 이어 C를 열어 같은 항목을 확인한다.
7. 원 서버 직접 조회 3건을 다시 대조한다. 없는 상품의 HTTP 상태, 준비 상태, 페이지 오류, DB 전후 스냅샷도 확인한다.

HTTP 응답과 화면 캡처, 게이트웨이 이벤트가 증거다. 원시 TCP 패킷 캡처로 개별 패킷 이동을 추적한 것은 아니다. 단계별 시각화의 `TCP X`는 같은 연결의 재사용을 설명하는 표기이며 실제 소켓 번호가 아니다.

### 수정 전 이벤트

시간은 첫 A 요청의 게이트웨이 전송 이벤트 기준이다. 각 숫자는 이벤트 기록 시점이며 네트워크 패킷의 송수신 시각이나 운영 환경 지연 추정치가 아니다.

| 상대 시각 | 기록된 동작 | 연결 번호 | 관측 의미 |
| --- | --- | --- | --- |
| 0.000ms | A `/products/1` 전송 | 1 | 원 서버 연결에서 A 조회 시작 |
| 17.363ms | A 응답 대기 작업 취소 | 1 | 원 서버의 SQL 작업 취소를 뜻하지 않음 |
| 21.451ms | 고객 연결 종료 처리 기록 | 해당 없음 | 고객 측 취소 확인 |
| 62.659ms | B `/products/2` 전송 | 1 | 미완료 A와 같은 원 서버 연결 사용 |
| 70.538ms | B 작업의 응답 읽기 완료 기록 | 1 | 실제 B HTTP 응답 본문은 상품 1 |
| 439.413ms | C `/products/3` 전송 | 1 | 같은 연결 재사용 |
| 447.991ms | C 작업의 응답 읽기 완료 기록 | 1 | 실제 C HTTP 응답 본문은 상품 2 |

`origin_complete` 로그의 `path`는 현재 게이트웨이 작업의 요청 경로다. 이 이벤트만으로 응답 상품이 맞다고 판단하지 않고 실제 HTTP JSON을 대조했다.

## 코드로 확인한 원인

`OriginPool.exchange()`는 연결을 획득한 뒤 `complete=False`로 시작한다. 요청 바이트를 쓰고 `drain()`을 거친 후 `read_response()`로 상태·헤더·본문을 읽는다. `drain()`은 송신 버퍼 흐름 제어이며 HTTP 응답 완료를 확인하는 동작이 아니다.

응답 전체를 읽으면 `complete`에 `response[3]`, 즉 읽은 응답의 재사용 가능 여부를 저장한다. 따라서 이 변수는 단순한 TCP 연결 성립 여부가 아니다. 응답을 다 읽어도 서버가 `Connection: close`를 지시했다면 `False`다.

고객 연결이 먼저 종료되면 `serve()`의 요청 처리기가 `exchange()` 작업을 취소한다. 응답 읽기가 끝나지 않은 경로에서는 `complete=False`가 유지되고, `finally`가 `release(channel, complete)`를 호출한다.

장애 코드의 `release()`는 전달된 값 대신 `reusable=True`로 고정했다. 그 뒤 종료된 연결인지만 검사했으므로, 아직 살아 있으면서 A 응답이 미처리인 연결도 `idle`에 들어갔다. B가 그 연결에 새 요청을 보내면 다음 응답인 A를 읽고 B 고객에게 반환했다. 서버의 응답 순서가 뒤집힌 것이 아니라, A를 기다리던 작업을 제거한 뒤 응답 순서와 대기 작업의 대응을 잃었다.

이 설명은 이 경로의 HTTP/1.1에 관한 것이다. 연결별 응답 대응과 재사용 시 본문 읽기 요건은 [RFC 9112의 요청·응답 대응 규칙](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.2)과 [지속 연결 규칙](https://www.rfc-editor.org/rfc/rfc9112.html#section-9.3)에 해당한다.

## 선택한 수정과 검토한 대안

선택한 수정은 `OriginPool.release()`에서 `reusable`을 전달받은 `complete` 값으로 결정하는 것이다. 미완료·취소·실패 연결과 재사용할 수 없는 응답의 연결은 닫고, 응답을 끝까지 읽은 재사용 가능 연결만 풀에 반환한다.

| 선택지 | 논의한 이유 | 결정과 실행 여부 |
| --- | --- | --- |
| 미완료 연결을 닫고 다음 요청에 새 연결 사용 | 기존 코드가 이미 완료·재사용 여부를 계산한다. 취소된 응답을 추가로 기다리지 않아 B가 A의 완료에 묶이지 않는다. | 선택·구현·검증 완료. 정상 연결 재사용도 유지한다. |
| 요청마다 항상 새 연결 생성 | 같은 연결이 기능적으로 필수인지에 대한 질문에서 가능한 방식으로 설명했다. | 구현하지 않았다. 정상 연결까지 재사용을 없앨 필요가 없고 성능 비교도 수행하지 않았다. |
| A 응답을 끝까지 받아 버린 후 재사용 | 연결의 HTTP 응답 경계를 다시 맞출 수 있는 대안으로 설명했다. | 구현·실험하지 않았다. 취소된 요청의 잔여 응답을 기다리고 별도 정리 작업을 관리해야 한다. |
| 원 서버·DB의 A 작업 자체를 취소 | 고객이 결과를 필요로 하지 않으면 서버도 취소해야 하는지 질문했다. | 구현하지 않았다. 원 서버 작업이 계속되더라도 해당 연결을 후속 요청과 분리하면 이번 오응답을 막을 수 있다. |
| 요청 상품 ID와 응답 JSON ID를 프론트나 게이트웨이에서 비교 | 응답을 받은 뒤에도 잘못된 상품임을 판별할 수 있는지 설명했다. | 사후 감지 대안이며 구현하지 않았다. 미완료 연결은 응답 내용을 추측하기 전부터 재사용 불가로 판단할 수 있다. |

### 실제 TCP 회귀 테스트

`tests/unit/test_gateway_connection_lifecycle.py`는 실제 로컬 TCP 서버를 사용한다. 첫 A 요청을 대기시킨 상태에서도 취소 이후 B·C가 정확한 응답으로 완료되는지 검사한다. 응답을 흉내 낸 객체만 반환하는 테스트가 아니다.

| 시나리오 | 수정 전 | 수정 후 |
| --- | --- | --- |
| A의 응답 헤더 전송 전 취소 → B·C 조회 | 후속 요청 대기 시간 초과 | 통과 |
| A의 일부 본문 전송 후 취소 → B·C 조회 | 후속 요청 대기 시간 초과 | 통과 |
| 정상 응답 후 같은 원 서버 연결 재사용 | 통과 | 통과 |
| `Connection: close` 응답 후 게이트웨이가 원 서버 연결 종료 | 연결 종료 대기 시간 초과 | 통과 |

신규 테스트는 수정 전 3개 실패·1개 통과에서 수정 후 4개 모두 통과했다. 기존 HTTP 응답 경계 검사 5개도 함께 실행해 총 9개가 통과했다. 기존 검사 범위는 중간 103 응답, chunked 본문, HEAD, 304, 연결 종료로 끝나는 본문이다.

추가로 변경한 Python 파일 두 개의 Ruff 검사를 통과했다. 최초 Ruff 실행은 읽기 전용 소스 경로에 캐시를 쓰려다 실패했으며, 캐시를 비활성화한 동일 범위 검사로 통과했다. 코드 문제로 인한 실패로 기록하지 않는다.

수정 후 기존 검증기를 `python -m lab_suite.operator check --expect healthy --fresh`로 실행했다. 실제 Linux Chromium에서 정리함과 텀블러의 이름·가격·상품번호를 화면 캡처와 HTTP 응답으로 확인했다. 검증 시점의 런타임 파일 해시, 컨테이너 안의 실행 파일 해시와 커밋 대상 파일이 일치했다.
